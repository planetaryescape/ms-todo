# 11: Decision log

Every decision from the planning session on 2026-09-24, **including the options we rejected and the reversals**, so a later agent understands how the design got here and doesn't argue its way back into an option we already rejected. BK is the decision-maker. Entries marked "BK" are his calls. Change a decision only by adding a new entry that replaces the old one.

## The arc, briefly

1. BK asked whether Microsoft To Do has a usable API. Research: yes. Graph v1.0 covers nearly everything, sign-in has to be delegated, and the old Outlook Tasks API is dead.
2. We asked whether to build or adopt. We first leaned towards **adopting an existing CLI and wrapping it in a skill**, reasoning that sign-in was the hard part and someone had already written it.
3. A code review of the best Python CLI found silent truncation, crashes on errors and a client-secret sign-in flow. We then leaned towards the TypeScript MCP server. Its review found a third-party client ID, a lossy move and the hidden device-code hang.
4. **BK changed the premise:** a coding agent does the build, so code is cheap. Don't accept a tool's flaws to avoid building one. That's now a global rule in BK's AGENTS.md. So: build our own.
5. BK pointed at his Rust projects mxr and spotuify. A study of both showed **mxr already has a working Microsoft device-code sign-in**, so Rust won.
6. The scope grew to the full API surface, a cache for a very fast TUI, and features the API lacks built on top: My Day, folders and assignment. Sharing and task assignment were first included, then sharing was dropped.
7. We proposed no daemon, then reversed that when BK asked what it was optimising for.
8. My Day went from a special list, to copies of tasks, to an Outlook category, and then, when the phone turned out not to show categories, to a date in our extension, mirrored on the phone through the due date (D-037).
9. Todoist-style natural language: deterministic, with the LLM deferred.
10. BK will build on a different machine, so this blueprint exists to carry the whole session.

## Decisions

### D-001: Build our own; don't adopt an existing tool. (BK)
- **Options rejected:** (a) wrap underwear/microsoft-todo-cli in a skill; (b) use MAG-Cie/mcp-microsoft-todo as an MCP server, configured with our own client ID.
- **Why:** (a) truncates lists silently past 100 tasks, crashes with a traceback on Graph errors, uses a client-secret flow where you paste the redirect URL, and looks things up by name. (b) uses a third-party client ID by default, has a lossy `move_task`, hangs silently on device code, carries the context cost of 28 MCP tools, and is MCP at all (see D-008). Details and commit SHAs are in `docs/research/prior-art.md`.
- **Principle (BK):** "Writing code is relatively cheap. No need to needlessly take on disadvantages." Recorded globally as: *weigh a tool's flaws against ongoing maintenance, not against initial build time.* A To Do client needs little maintenance once it's built.

### D-002: Rust, following mxr and spotuify. (BK proposed; agreed)
- **Option rejected:** TypeScript on bun, BK's default for new projects.
- **Why Rust:** mxr's `crates/provider-outlook/src/auth.rs` already implements Microsoft device-code sign-in, so the hard part is adapted rather than written. spotuify shows the copy-from-mxr approach works (rate limiting, output, exit codes, IPC). It uses the same release setup (release-please, Homebrew, `install.sh`). ratatui is the natural TUI. It ships as one static binary.
- **What TypeScript would have given:** the MAG&Cie code could have been adapted directly. That stopped mattering once mxr turned out to have the equivalent.

### D-003: Cover the whole API, plus the features the app has that the API lacks. (BK)
- BK doesn't know yet exactly how he'll use it, so every capability should be ready. The To Do domain is small, so this is bounded.
- We noted the counter-principle ("don't ship features just because you can"). BK decided deliberately.

### D-004: Device-code sign-in, BK's own app registration, `/common`, no secret.
- **Options rejected:** a client-secret web flow (the Python CLI; the secret expires and has to be stored); PKCE with a loopback listener (works, but needs a local port and a browser, and device code suits a terminal and SSH); a third-party client ID (MAG&Cie; a trust and availability risk); mxr's `consumers`/`organizations` split (`/common` covers both with one registration).

### D-005: A local SQLite cache is the read path, with instant local writes. (BK: "I want the cache that will allow the TUI to be blazing fast.")
- **Option rejected:** reading straight from Graph, which puts network latency on every keypress.

### D-006: Have a daemon. (Replaces an earlier "no daemon" proposal.)
- **Earlier proposal:** no daemon. The TUI syncs itself, CLI commands do a quick delta before reading, and SQLite WAL handles several processes.
- **BK asked:** "Are you sure we should skip the daemon? What are you optimising for?" The honest answer was *fewer moving parts*, which is the same "code is expensive" bias D-001 already rejected.
- **Why a daemon:** fast CLI and agent reads; the outbox has to keep going after the TUI exits; Microsoft replaces refresh tokens on use, so only one process should refresh; events can be pushed; the My Day rollover needs scheduling. mxr and spotuify already solved the daemon's costs.

### D-007: Delta polling; no webhooks.
- **Option rejected:** Graph change notifications (`todoTask` subscriptions exist in v1.0, lasting up to about 3 days). They need a public HTTPS endpoint, which isn't worth it for a local tool when delta gives the same freshness.

### D-008: No MCP server. (BK)
- BK: "I'm personally not a fan of MCP servers, especially when the agent has access to a full CLI that it can control fully. If you want an MCP, you'd have to convince me why we need it."
- The only argument for one was clients without a shell (Claude Desktop, mobile). BK doesn't need those. The CLI plus a skill covers agents, and it costs context only when used.
- Revisit only if a real client without a shell needs it.

### D-009: The CLI is the canonical surface; every feature is in the CLI. (Taken from spotuify.)

### D-010: Crates kept to about 10, not 18–28.
- mxr and spotuify are big because of mail and playback. Borrow their patterns, not their size.

### D-011: SQLite FTS5 for search, not Tantivy.
- Task counts are in the thousands at most. FTS5 lives inside the same database, with no second index to keep in sync or unlock. That avoids the Tantivy lockfile problems noted in spotuify's AGENTS.md.

### D-012: The token goes in a 0600 file, not the macOS Keychain.
- Follows mxr's Outlook provider and spotuify. Keychain access from a background daemon can prompt the user or fail when nobody is at the machine (mxr's Gmail path needed a disk fallback for exactly this). A token file is simpler and fits a local-first design. Revisit if BK wants the Keychain.

### D-013: The build happens on another machine; this blueprint carries the session. (BK)
- **Option rejected:** exporting the session transcript. It's local, noisy, and full of claims that were later reversed. A refined blueprint with a decision log is what the next agent actually needs.

### D-014: Don't build sharing. (BK: "we can skip sharing, I don't share my todos with anyone anyway.")
- We had analysed two options: (1) use lists already shared through the official app (`Tasks.ReadWrite.Shared`, `isShared`), or (2) build our own sharing backend, which would be a product with hosting and security costs, not a CLI feature.
- Result: neither. We still display `isShared` and `isOwner`.

### D-015: My Day is an Outlook category plus an extension date. (BK approved)
- **Option 1, rejected:** a special "My Day" list whose tasks are moved in and out. Graph has no move operation; recreating a task loses its ID, steps, attachments and created date.
- **Option 2, rejected (BK):** copies of tasks in a "My Day" list, linked to the originals. BK: "I don't want the double items thing." The phone would show every task twice.
- **Option 3, rejected:** an extension only. The phone couldn't see it.
- **Chosen:** the category "My Day" (visible and filterable on the phone; `categories` is a first-class property, so delta sync definitely picks it up), plus `myDay: date` in the ms-todo extension, and a daily rollover in the daemon. The task never leaves its list. Cost: `MailboxSettings.ReadWrite`, which we need anyway for `@label`.
- The app's own My Day can't be reached through the API and is left alone.
- Note (2026-09-24): the phone-visibility premise is unverified pending the S7 phone check (see D-030).
- **Replaced by D-037:** the phone shows no categories, so the category is dropped. My Day lives in our extension and reaches the phone through the due date.

### D-016: Deterministic natural-language parsing; the LLM is deferred. (BK: "leave llm parsing for now")
- BK wanted Todoist-style quick add: deterministic first, then maybe an optional small local LLM for richer parsing.
- **Deferred because:** build the deterministic parser, see where it actually falls short, and then decide. The `QuickAddParser` trait keeps room for an LLM backend (Ollama or llama.cpp with a fixed JSON output format) at no cost now.

### D-017: Todoist p1–p4 maps to Graph's three importance levels.
- p1 = high, p2 and p3 = normal, p4 = low. That's lossy: Graph only has `low`, `normal` and `high`. Storing the original p-level in the extension is possible if BK wants the distinction (Q3).

### D-018: Parse by default, `--no-parse` for agents, explicit flags win.
- This prevents "Email Friday's report" from getting a due date of Friday when an agent adds it.

### D-019: Moving a task is a full copy that checks itself before deleting.
- **Option rejected:** MAG&Cie's recreate-then-delete, which loses children and leaves duplicates on failure.

### D-020: Folders go in list extensions; assignment goes in task extensions.
- Invisible to the official apps, which is accepted. Assignment pairs with the real `waitingOnOthers` status, which is visible.

### D-021: Name `ms-todo`, repo `planetaryescape/ms-todo`, public, dual MIT and Apache-2.0 like mxr. (BK)
- An unrelated tiny `visionik/mstodo` exists. Its name is close but doesn't clash.

### D-022: Quick add goes to "Tasks" by default; you can name a list. (BK)
- With no `#List` in the text and no `--list` flag, the task goes to the built-in "Tasks" list (`wellknownListName = defaultList`), in both the CLI and the TUI. `#List` and `--list` always override that.
- **Option rejected:** defaulting to whichever list is selected in the TUI. The TUI and the CLI would behave differently.

### D-023: No location support. (BK: "I've never really needed to put location to my tasks")
- The API has no location field or location reminders anyway. We won't store location text in the extension, and the parser has no location rule.

### D-024: The My Day rollover is at midnight, configurable. (BK)
- The default is 00:00 local time. `my_day.rollover_time = "HH:MM"` in config.toml changes it, for example "04:00" for late nights.

### D-025: Bundle BK's client ID, and encourage users to use their own. (BK)
- Release builds bake in BK's Entra client ID with `option_env!("MS_TODO_CLIENT_ID")` (mxr's `BUNDLED_CLIENT_ID` pattern), so `brew install` then `ms-todo auth login` works immediately. The ID isn't a secret.
- The README, `docs/`, and the first run of `ms-todo auth login` recommend registering your own app, with a short guide, and explain why: with the bundled ID, users consent to BK's app registration, and its availability depends on BK. `auth.client_id` in config or `MS_TODO_CLIENT_ID` overrides the bundled ID. `ms-todo auth status` shows which one is in use.


### D-026: Dates are read by a custom rule-table scanner, not a library. (Phase 0, from S8)
- **Replaces:** the plan in [06](06-natural-language.md) to use `clockwords`, with `interim` as a fallback. That plan had no entry of its own here. D-016 (deterministic, LLM deferred) still stands.
- **Options rejected:** (a) `clockwords` 0.4.0, 33% of 127 graded phrases: no absolute dates and no bare weekdays. (b) `interim` 0.2.1, 24–39%: whole-string only with no spans, matches words on three-letter prefixes (`Monitor` → Monday), doesn't roll dates forward. (c) `chrono-english` 0.2.1, 35%: the same flaws as `interim`, and no bare times. (d) `whichtime-sys` 0.1.0, the best at 53%: needs `chrono::Local`, reads weekdays towards the past, and still takes `Sat nav` as a date. (e) A library plus patch rules: the missing pieces are the core of the job (absolute dates, spans, leaving titles alone), not edge cases.
- **Why:** finding a date inside a task title without eating the title is narrow, well specified and easy to test with a corpus, and no crate does it. A scanner of roughly 500–700 lines, with ordered masking passes, serves quick add, `!`, `start` and the date flags alike. Evidence: [S8](../research/spikes/S8.md).

### D-027: Due and start dates are dates only; a time goes to the reminder. (Phase 0, from S11)
- **Replaces:** the `nlp.time_sets_reminder` setting in [06](06-natural-language.md), which is dropped. It had no entry of its own here.
- **Options rejected:** (a) keeping the setting with `false` as an option. Graph throws away the time on `dueDateTime` and `startDateTime`, so `false` would silently lose the time. (b) Storing the time in our extension. The phone couldn't see it, and nothing would remind BK.
- **Why:** a reminder is the only place Graph keeps a time. So "tomorrow 5pm" sets the due date to tomorrow and a reminder at 17:00. The cache stores due and start as local dates and reads them by rounding to the nearest local midnight, because BK's data holds due dates written as midnight in several zones ([02](02-data-model.md#principles)). `start` without a due date also sets the due date, so the parser warns. Evidence: [S11](../research/spikes/S11.md).

### D-028: The outbox has an "unknown outcome" state. (Phase 0, from the reuse-map check)
- **Options rejected:** (a) treating every failure as temporary or permanent, as [04](04-sync-cache.md) first did. A create POST that times out or gets a 5xx after Graph accepted it would be retried and make a duplicate task. (b) An idempotency key. Graph To Do doesn't support one. (c) Never retrying creates. An offline or throttled create would then need a person to retry it.
- **Why:** state `unknown` means "don't resend". The HTTP client never retries a create or a recurring completion automatically after a timeout, 5xx or 408; it retries only on a 429, a 401 then refresh, or a connection failure before sending. Operations still `inflight` at daemon start become `unknown` too. The rule is to adopt only a result we can attribute: a task create carries its `op_id` as `opId` in our extension, inline in the POST (S13), so each sync round's lookup can match it exactly, for up to 24 hours. A recurring completion stays `unknown` for the user even if a GET shows the due date moved, because the phone could have done that; `outbox list` shows what was seen. Checklist-item and linked-resource creates are never matched by content. Anything not attributed goes to the user (`outbox retry` or `outbox discard`); it's never re-sent or deleted automatically. A duplicate `opId` seen in sync raises `DuplicateDetected` for the user. The invariant: not finding something never allows a replay or a delete. This follows mxr's `plans/014-send-outcome-recovery.md` and `plans/023-interrupted-mutation-jobs.md`. Details: [04](04-sync-cache.md#unknown-outcome-d-028).

### D-029: Task children sync through delta alone; extension content is fetched after each round. (Phase 0, from S1 and S2)
- **Settles:** the open choice between strategies (a) and (b) that [04](04-sync-cache.md) left to S1 and S2.
- **Options rejected:** (a) as first written: `$expand=checklistItems,extensions` on delta. Checklist items are inline anyway, and delta never returns extensions, with or without `$expand`. (b) Re-fetching children in batches for every changed task, plus a slow background sweep. Not needed: every child change bumps the parent, so delta never misses one.
- **Why:** checklist items and linked resources arrive inline in delta, attachments flip `hasAttachments`, and extension changes bump the parent without their content. So delta finds every change, and the only extra work is a filtered-`$expand` fetch of extension content after each round. Details: [04](04-sync-cache.md#children-of-a-task). Evidence: [S1](../research/spikes/S1.md), [S2](../research/spikes/S2.md).

### D-031: Clients use the daemon protocol only; the TUI doesn't read SQLite. (BK, 2026-09-24)
- **Replaces:** "the TUI may read SQLite directly" in [01](01-architecture.md), the read-only connection pool in [08](08-tui.md), and "the TUI only ever reads SQLite" in [README](README.md). None had an entry of its own here.
- **Option rejected:** direct SQLite reads for the TUI's hot path.
- **Why:** once one client reaches past the protocol, the protocol stops being the product, and the next client can't be built cleanly (vault: `Building Great CLIs`, "can the TUI just reach into the store directly… the answer is no"; `Mxr`). The TUI seeds from a daemon snapshot (spotuify's `ClientSeed`) and then applies `EntityChanged` events. A Unix-socket round trip is about 5–10 µs (vault: `Local IPC vs HTTP`), so the latency budget stands. Only the daemon touches `store`, and the boundary test enforces it.

### D-032: Phase 1 ships a minimal daemon, not a direct-mode CLI. (BK, 2026-09-24)
- **Replaces:** Phase 1's "CLI without a daemon yet, in direct mode" in [10](10-roadmap.md).
- **Option rejected:** direct mode first. The CLI would become a second token refresher, breaking "only one process refreshes" in [01](01-architecture.md#why-a-daemon), and it would be built against internals rather than the protocol.
- **Why:** "Build the CLI client against the documented protocol, not against private daemon internals" (vault: `API-First Design`). Phase 1 builds the protocol, socket server, auto-start and a daemon that owns sign-in and refresh, plus `auth`, `lists list`, `tasks list`, `raw` and `sync` over IPC. Phase 1 syncs by full enumeration only (below); **delta** sync, the outbox and mutations start in Phase 2. Phase 1's completion check is unchanged.
- **Phase 1's cache:** the daemon runs a full enumeration of lists and tasks on start and on `ms-todo sync` (page to the end, upsert, tombstone what wasn't seen, by [04](04-sync-cache.md#reconciliation-after-a-lost-delta-token)'s rules), and reads are served from the store. Phase 2 adds delta on top, and the enumeration becomes its reset path, so nothing is thrown away.
- Note (2026-09-24): the cache now arrives in rung 3a, and rung 1's daemon reads straight from Graph. See D-034.

### D-034: The roadmap is a ladder of usable releases. (BK, 2026-09-24)
- **Replaces:** the component phases in [10](10-roadmap.md) (Foundation; Daemon, sync and outbox; Full API surface; TUI; Custom features and natural language; Ship). Phase 0 stays as it was.
- **Option rejected:** building by component. Nothing would be usable until the TUI phase, and nothing would ship until the last one.
- **Why:** BK's rule is skateboard → car (vault: `Skateboard MVP`, `Shippable Increment Per Session`). Each rung is a released, installable tool that lets BK do something new from start to finish, and fits one working session. Ceremony is pulled into rung 1, and each rung has at most two new unknowns.
- **The ladder:** 1 skateboard (see my tasks), 2 scooter (capture and finish tasks), 3a bicycle (instant reads), 3b live sync, 4 e-bike (offline, never lose a write), 5 motorbike (TUI), 6 car (quick add), 7 convertible (My Day), 8a–8e rocket (the rest of the API, one capability per release).
- **Foundation turns:** up to about three named foundation turns may come before the first usable rung, each saying what it makes possible and ending with something runnable or checkable. ms-todo has one, F1 (install and sign in), so rung 1 arrives in turn 2.
- **Trade-off, accepted:** rung 1's daemon reads straight from Graph, and rung 3a replaces that read handler with the cache. Entity `id`s change meaning at rung 3a (Graph ID to local ID), with a `schema_version` bump. That's rework `Skateboard MVP` accepts on purpose: "more re-work in exchange for de-risking". D-031 and D-032 still hold: clients only ever talk to the daemon, and the daemon is the only token refresher.

### D-035: Config lives in `~/.config/ms-todo` (XDG) on every Unix, not the macOS Application Support dir. (BK, 2026-09-24)
- **Replaces:** `<config_dir>/ms-todo/config.toml` in [01](01-architecture.md#files), which `dirs::config_dir()` put in `~/Library/Application Support` on macOS.
- **Rule:** `config.toml` in `$MS_TODO_CONFIG_DIR`, else `$XDG_CONFIG_HOME/ms-todo`, else `~/.config/ms-todo`. Data (the token, logs and later the cache) stays in the platform data directory.
- **Why:** most CLIs keep config there, on macOS too.

### D-036: Rung 3a's cache, as built. (Rung 3a build, 2026-09-24)
- **Refines** [02](02-data-model.md)'s draft tables, as that document invited, and fills in rung 3a details [04](04-sync-cache.md) left open. Nothing here reverses an earlier decision.
- **Pending work before the outbox.** 04 never tombstones rows with pending outbox work. Rung 3a has no outbox, but the daemon's own synchronous writes can still race a pass that fetched earlier. So each row records the value of a `local_rev` counter when the daemon last wrote it, each scope reads the counter before it fetches, and applying the scope leaves alone every row written since: no overwrite, no tombstone. Rung 4 adds "has an outbox operation in `pending`, `inflight` or `unknown`" to the same exemption. A clock would do the same job less reliably (vault: `Faster Code Breaks Coarse Clocks`).
- **Which tasks need their extension fetched:** those whose etag differs from `hydrated_etag`, the etag at which the extension was last fetched. The first sync fetches every task's (BK's 654 tasks: about 17 seconds); later passes fetch only changed tasks. Lists never need it: the list enumeration itself carries the filtered `$expand` (S2), so one request covers both.
- **The cache is private:** the data directory is 0700 and `ms-todo.db` and its `-wal` and `-shm` files are 0600, repaired on every start, like the token and the socket.
- **Our extension is a column** (`extension_json` on `lists` and `tasks`), not rows in 02's `extensions` table, which is for rung 8e's general `extensions` command.
- **Idempotency keys live in their own table**, `idempotency_keys`, since there's no outbox to hang them on. A key is released only when the request certainly changed nothing on Graph: a failure that proves it (invalid input, not found, conflict, rejected, rate limited, sign-in) before any task was changed. Everything else is kept. A failure that may have followed a change on Graph (a network error or 5xx, or the cache write failing after Graph took the change) is recorded as `outcome_unknown` with the `op_id`, so a repeat never sends it again. A cache write that fails after Graph took a change is `outcome_unknown` with or without a key. After a restart, a key whose request never finished gets an `outcome_unknown` result, kept for 24 hours.
- **Reads of a scope that has never synced.** While a sync runs, the answer is `initial` with no items. With nothing running (the last attempt failed), the read runs a sync and answers from that, so it reports the failure (for example exit 4, signed out) instead of an `initial` that would never become `ready`. Writes wait for the scope's first sync, because they resolve names in the cache.
- **Without `--list`, a task is looked up only in the cache**, by local or Graph ID. Rung 2 asked every list for an ID it hadn't seen; with the cache that fallback is gone, and a task added elsewhere since the last sync is `not_found` with a hint to run `ms-todo sync --wait`.
- **Not built in rung 3a, and still to be placed:** the local read filters (`--status`, `--due`, `--importance`, `--search` through FTS5, `--sort`, `--limit`), `EntityChanged` events with the 500-ID cap and `ResyncNeeded`, `sync --list`, attachment metadata (it needs rung 8b's table), and the optional launchd and systemd files. The build brief for rung 3a left them out.

### D-037: My Day lives in our extension, and reaches the phone through the due date. (BK, after the phone check, 2026-09-24)
- **Replaces:** D-015's Outlook category and D-030's colour.
- **Why:** BK's phone check (S7) found that the iOS To Do app shows no categories at all, so a "My Day" category would be invisible on the phone. ### D-038: Rung 3b's delta sync, as built. (Rung 3b build, 2026-09-24)
- **Fills in** details [04](04-sync-cache.md#delta-sync) left open. Nothing here reverses an earlier decision.
- **A whole read is a fresh delta round.** A scope's first pass, and its reset, page `…/delta` with no token to the end: that's every item plus a `deltaLink`, in one set of requests. The plain `/tasks` enumeration is no longer used. A whole read tombstones what it didn't see; a delta round tombstones only `@removed` entries and extension fetches that answer 404.
- **Lists always apply an enumeration.** Delta never carries extensions (S2), so when `lists/delta` names any list, the one `GET /me/todo/lists` with the filtered `$expand` that 04 fetches for extensions is applied as a whole read (upsert, tombstone the rest), minus lists delta called removed. A lists delta round that names nothing just checkpoints.
- **Cursors live in `sync_state`** (`delta_link`, `last_delta_at`, migration `0002`). A scope with no link is in enumeration mode; `doctor` shows each scope's `mode` and `last_delta_at`. A 410 or "Badly formed token." drops the link at once, so a reset that then fails stays in enumeration mode.
- **404 and 5xx keep the link.** The Graph client already retries a 5xx with backoff inside the request. After that, or on a 404, the scope fails and the next pass replays the same link. A tasks-delta 404 first checks `GET /me/todo/lists/{id}`: a 404 there tombstones the list and its tasks and drops its cursor (S4).
- **Cadence:** a pass every 20 seconds while any client is connected or has sent a request in the last 10 minutes, otherwise every 5 minutes, measured from the end of the last pass. The first request after an idle spell brings the next pass forward. No `sync.interval_secs` setting yet.
- **Not built, and still to be placed:** `--fresh`, the TUI focus hint, attachment metadata (rung 8b), and syncing after the outbox sends (rung 4).

### D-040: Rung 4's outbox, as built. (Rung 4 build, 2026-09-24)
- **Fills in** [02](02-data-model.md#outbox-semantics) and [04](04-sync-cache.md#instant-local-writes), and **replaces** two details of 04, marked below.
- **The table** (migration `0003`): one row changes one task. A command that changes several tasks shares its `op_id` as `command_id`; its first row's `op_id` is the command's, the rest are `<command_id>.<n>`. A create's `op_id` is the `opId` in our extension. Rows keep a queue order (`seq`), what is sent (`op`: create, update, delete) apart from what the user asked (`action`), `undoes_command_id`, `sent_at`, `unknown_since`, a `note` for the user, and `finished_at`. There's no `client_request_id` column: keys stay in `idempotency_keys` (D-036), and the store keeps a key while any of its command's operations is unresolved and for 24 hours after. A discarded row is deleted.
- **Order:** every operation waits for the latest unresolved operation on its task (`depends_on_op_id`), not only an edit for its create, so each task's operations go out in order. Graph's answer to one is written with the fields of the task's later queued operations on top. A temporary failure (network, throttling, a 5xx on an idempotent request, sign-in) holds the whole queue for a backoff of 2 s doubling to 5 minutes; a new write is tried at once.
- **Replaces 04's field-level merge.** 04 keeps the local values of only the fields pending operations touch and takes the server's for the rest. As built, a sync pass leaves a task with any `pending`, `inflight` or `unknown` operation alone entirely (next to the `local_rev` check of D-036). What it skipped comes back with Graph's answer to the operation, which is the whole current task. When an outcome is decided without Graph's copy (a rejection, or discarding an `unknown` update), the task's list drops its delta link, so the next pass reads it whole. Simpler, and nothing is lost.
- **Attributing an `unknown` create looks in the cache** rather than sending 04's `$filter=lastModifiedDateTime` GET: every new task sync sees has our extension fetched (hydration), so after each pass the worker looks for a live cached task whose extension holds the `opId`. The rest is as 04 says: an exact match only, the list-liveness GET before adopting, an atomic merge into the original row, and looking stops after 24 hours, when the operation is flagged. Two matches are recorded in the operation's `note` as a duplicate for the user; no `DuplicateDetected` event yet.
- **The ghost-write check** sends one `GET /me/todo/lists/{l}` per distinct list per round, one after another, not in a `$batch`. A GET that fails other than with 404 leaves the create `unknown`, to be attributed later.
- **Keeps rung 2's conflict rule, instead of 04's last write wins.** A 412 on a field the server also changed fails the operation with kind `conflict`, rolled back and kept, rather than overwriting and sending `ConflictOverwritten`. The user can `outbox retry` it.
- **What waits on a failed or discarded operation fails with it,** transitively and in the same transaction, with a note naming the cause. An undo's re-create queued behind a delete that Graph then rejects would otherwise make a second copy of a task that still exists.
- **Retry, discard and the worker's claim are conditional updates** (`… WHERE op_id = ? AND state = ?`). `retry` moves only `failed` or `unknown` to `pending`; `discard` removes only `pending`, `failed` or `unknown`. If the state moved in between, nothing changes and the answer is `conflict` (exit 5).
- **The daemon opens the database before it binds its socket,** so a daemon that can't start leaves no socket for a client to connect to and have reset (Linux). The client always sees the exit status instead.
- **`WriteRejected`** is a protocol event on a broadcast channel with no subscriber until the TUI (rung 5); it's also logged, and the operation stays `failed` in `outbox list`.
- **Undo:** with no `OP_ID`, the latest command that isn't an undo and hasn't been undone (there's no per-client identity yet). An undo is a command with `undoes_command_id`, so it can be undone in turn. Undoing a delete keeps the task's local ID and gets a new Graph ID. Undoing a recurring completion deletes the copy named by `--copy` and PATCHes the due date back. Rejected operations are skipped; an `unknown` one must be resolved first.
- **A request that fails frees its idempotency key.** Queueing is one local transaction, so a failed request changed nothing.
- **A database newer than the binary** makes the daemon exit with status 78 (`EXIT_DATABASE_TOO_NEW`), which the client that started it reports as error kind `database_too_new`, exit 1.
- **`sync_state` everywhere:** a `SYNC` column in the tasks table and a `sync_state` column at the end of the tasks CSV. Precedence: `unknown`, then `pending`, then `failed`; a `failed` operation marks its task until it's discarded or retried.
- **Not built, and still to be placed:** move recovery (rung 8), `ConflictOverwritten`, the `outbox.unknown_lookup_hours` setting, pruning `done` operations, the TUI's undo picker (rung 5), and noting a lost answer to a connect that was retried: a create interrupted while its connection is being retried is `unknown` after a restart, though it never reached Graph.

### D-041: Search uses SQLite FTS5. (Rung 4b build, BK, 2026-09-24)
- **Reaffirms** D-011. Tantivy was rejected again: tasks are small, FTS5 lives in the same database and the same transactions as the cache, and there's no second index to keep in step or rebuild.
- **As built** (migration `0004`): a regular FTS5 table, `tasks_fts(title, body)`, keyed by `tasks.rowid`, with the `unicode61 remove_diacritics 2` tokenizer and `prefix='2 3'`. It keeps its own copy of the text, so `snippet()` works and a tombstoned task is simply absent. Triggers on insert, update (only when the title, the notes or tombstoned-ness change) and delete keep it current, so every write path, sync or outbox, is covered without code in each.
- **The notes are indexed as plain text**, from a new `tasks.body_text` column the store fills on every write: an html body is rendered to text with `html2text` (as mxr does), a text body is kept as it is. SQL can't render HTML, so the migration fills text bodies and indexes every live task, and the store fills html ones when it opens the database. A partial index over the rows still missing `body_text` keeps that check free on every later open.
- **Ranking:** bm25 with the title weighted 10 to the notes' 1, then newest first.
- **Queries** are FTS5's syntax, but the CLI's input is rewritten first: each word is quoted (a trailing `*` kept outside the quotes), words of punctuation only are dropped, and an explicit `AND` goes between operands with no operator. So `e-mail`, `don't` and `milk (eggs OR bread)` work, and a plain query is all its words ANDed. What FTS5 still rejects (`OR milk`, an unclosed quote or parenthesis) is error kind `invalid_input`, exit 2.
- **Protocol 4:** `SearchTasks`, and `search` on `ListTasks`, which a protocol 3 daemon would ignore and answer with the whole list.
- **Across lists** the answer is `ready` once every list has synced once; before that it has what's cached, marked `initial`.
- **A VACUUM could renumber `tasks.rowid`** (the table has no `INTEGER PRIMARY KEY`), which would detach the index. ms-todo never runs one; anything that adds one must rebuild `tasks_fts` after it.
- **Closes** D-036's unbuilt `--search`.

### D-046: Auto-start fully detaches the daemon, and a zombie counts as exited. (Upgrade hotfix, 2026-09-25)
- **Why:** upgrading to 0.1.10 failed with "the daemon (pid …) didn't exit" while a 0.1.9 TUI was open. The TUI had auto-started the daemon as its direct child (`process_group(0)` only) and never waited on it, so the stopped daemon stayed a zombie, and `kill(pid, 0)` reports a zombie as alive.
- **Detach:** a client spawns the hidden `ms-todo daemon launch`, which calls `setsid()` and runs `ms-todo daemon run`. The launcher is the daemon's parent only during startup, so it can relay an early exit status (such as `EXIT_DATABASE_TOO_NEW`); the client kills and reaps it once the daemon is ready or startup fails, so the daemon's parent becomes launchd or init. A launcher whose client died exits after 30 seconds. No client keeps a `Child` for the daemon. Option rejected: a `pre_exec` double fork, because the workspace forbids `unsafe`.
- **A zombie counts as exited** in the stop wait: nothing is left to wait for, and only its parent can reap it, so clients already in the field can't block an upgrade. The probe reads `/proc/<pid>/stat` on Linux and runs `ps -o state=` on macOS (mxr's probe; `proc_pidinfo` needs `unsafe`). A stop still needs the socket unreachable as well (spotuify's rule).

- **`done`** is a new read, `CompletedTasks { since, until, list, folder, limit }`, answered from the cache through the daemon, never from Graph. `completedDateTime` is a **date**: Graph keeps midnight UTC of the day (S12; live on 2026-09-25, a completion at 03:29 BST was `2026-09-25T00:00:00Z`), so a completion's day is **Graph's UTC date** (`ms_todo_core::completion_date`, used by `done`, `completed_on` in JSON and CSV, and the TUI's Completed groups), and no time is shown or claimed. **Amended (review, 2026-09-25):** it was first read by the due dates' nearest-midnight rounding, which put `2026-12-10T00:00Z` on 11 December in Auckland (+13); a due date is midnight in the writer's zone, but a completion is midnight UTC. A value with a real time, which Graph hasn't been seen to send, is converted to the local zone and its date taken, with no rounding. Expected, not a bug: a task completed between midnight and 01:00 BST (or any time the local date is ahead of UTC's) shows on the UTC date, the day before, because that's the day Graph records. A completion Graph hasn't answered has no date yet: it counts as today's, comes first ("Not synced yet", `completed_on` null), and the Completed view's order now puts it first too (it was last), matching the TUI's list order.
- **Looking back** is a lean of `crates/nlp` (`ParseContext.lean`, `read_past_date`): a bare weekday is the latest one, today included, and a day and month with no year the latest one; `this week`, `last week`, `this month`, `last month` join the rule table (Mondays and 1sts, in both leans). Everything else reads as `--due` does.
- **Bulk changes reuse `ChangeTasks`** rather than a new request: `select: TaskSelect { due_before, folder }`, resolved in the daemon when the change runs (open tasks due before the day, in `list`, the folder or every list). One command, one operation per task under one `op_id`, as a multi-task complete already was. `reschedule` is a due-date edit; `tasks edit` takes several tasks, stdin or the selection, and refuses `--title` and `--body` for more than one. Option rejected: a `--where` expression language; `--overdue` and `--due-before` cover the pick and match `tasks list`'s planned `--due` filter. Option rejected: selecting in the CLI and sending IDs, which would make a repeat under an idempotency key a different request.
- **Confirmation:** a change that may reach more than one task is previewed first; more than one asks in a terminal and needs `--yes` elsewhere (exit 2), and after a yes the IDs shown are what runs, as `tasks delete` does.
- **Undo is per task for a change to several** (amends D-047's "nothing is queued"): the tasks whose field changed since are left alone and returned in `Applied.refused` (`{ id, title, reason }`), the rest are undone, and only when every one changed is the undo refused (`conflict`, exit 5). A one-task change is refused as before.
- **Undo puts a date back as its local day** (a bug found live, older than 5d): Graph gives a due date as a UTC instant (midnight London in summer is 23:00 the day before) and keeps only the date part of what it's sent (S11), so sending back the value it gave moved the date a day earlier. A due or start date not already at midnight in its own zone is now written as its local day's midnight in the user's zone, in an undone edit, a re-created task and a recurring completion's restored due date.
- **Protocol 7:** `CompletedTasks`, `ChangeTasks.select` and `Applied.refused`, so a client restarts an older daemon rather than send a selection it would read as a change to no task.
- **TUI:** the Completed view grouped by day; `S` "Set due date…" for the selection or the cursor's task (`e` `d` with a selection too) and `R` "Reschedule overdue to…" for the overdue open tasks on screen, both in the palette, both in the hint bar with the date editor's reading and preview, sending one `ChangeTasks`. The folder prompt's hint says "Enter on empty: no folder" (BK's usage).

### D-051: Rung 5e, moving tasks between lists, pulled forward from 8c; as built. (BK, rung 5e build, 2026-09-25)
- **Why now:** BK pulled `tasks move` forward from 8c. It's the one operation that can lose data, so correctness came before speed. **Replaces** 8c (steps and attachments stay product features of 8a and 8b; the move copies them at the Graph level). Reaffirms D-019 (a copy that checks itself before deleting) and D-028 (not finding something never allows a replay or a delete).
- **S14 changed the job, from the brief's per-child steps:** one POST creates the copy with every field, the checklist items (with `isChecked` and `checkedDateTime`), the linked resource and our extension carrying the move's own `opId` and `originalCreatedAt`, so the copy and all its children are one attributable create (S13). Only attachments are separate requests, one after another; the `$batch` chains S10 allowed for aren't needed. A task has at most one linked resource (S14). An upload session's bytes go to `<uploadUrl>/content` with the token. A recurring task's due and start dates are written as midnight of their local day in the zone its recurrence reports (a GET reports UTC), or Graph moves the copy's dates a day on; a one-off's as its local day in the user's zone (D-048's rule).
- **One outbox operation per task** (op `move`, action `move`, the row's list the target), with its steps saved in `outbox.progress_json` (migration `0005`): prepare (read the source, its extension and every attachment's bytes into a 0600 spool under the data directory; nothing is written, and an attachment over 25 MB is refused here), create, attachments, verify, delete, and roll back. `in_doubt` is saved before any create is sent and cleared with its answer; `delete_started` before the source's DELETE may be sent. A command's operations share its `op_id`, so one `undo` reverses a bulk move. Option rejected: a separate jobs table, which would duplicate the outbox's ordering, retry, discard, undo and idempotency.
- **The task keeps its local ID.** It shows in the target list at once; once the copy is created it takes the copy's Graph ID (merging any row sync made for it, as adoption does), and when the move is done it's the checked copy. Rolled back or discarded, it's back in its list with the source's Graph ID and content.
- **Verify** is: `GET /me/todo/lists/{target}` answers 200 (the ghost-write check); the copy read back holds every value S14 found a copy keeps, from the same field lists the POST is built from so the two can't drift (every field, dates as days, the reminder to the minute, each step's name, checked flag, `checkedDateTime` and `createdDateTime` to the second, every attribute of the link, our extension less `opId`; the task's own `createdDateTime`, which a copy never keeps, is left out on purpose), carries `originalCreatedAt`, and has the same attachments by name, byte count and sha256 (downloaded, since Graph's `size` isn't the byte count); and the source's etag hasn't moved since it was read. Any mismatch deletes the copy and keeps the source.
- **Failures, as 04 says:** a refusal before the delete rolls back (the partial copy deleted, the operation `failed`, `WriteRejected`, both lists read whole next pass). A create with no answer pauses the move `unknown`: the copy's create is looked for by its `opId` after each sync and, found in a live list, the move carries on; an attachment with no answer pauses it for the user (`flagged` at once, since nothing can attribute it). Nothing is deleted while paused. Once the DELETE may have started, the copy is never deleted: a resumed move GETs both and applies the four cases (source gone and copy there: done; both there: check the copy again against the source as it is now, and the target list, then delete, or, if the source changed meanwhile, delete nothing and pause for the user; source there and copy gone: rolled back; both gone: `unknown`, flagged, the whole task kept locally with its attachments in the spool). A source deleted on another device during the check leaves the checked copy as the task; a source *changed* during the move rolls back, keeping the change.
- **Right before the DELETE** the source is read once more and its etag compared with the one the copy was checked against; a change pauses the move with both kept. Task DELETE ignores `If-Match` (S6), so an edit landing between that read and the DELETE is still lost: accepted, [issue 004](../issues/004-move-delete-race.md).
- **`outbox retry`** of a paused move sends again what had no answer (the user's choice: an attachment may be attached twice, and then the check fails and the move rolls back, losing nothing); of a both-gone move, re-creates the task in the target list from the local copy; of a failed move, starts again. **`outbox discard`** puts a paused or not-yet-started move's task back where it was (a paused copy then arrives by sync as its own task; nothing is deleted), lets a both-gone task go, and refuses a move that has started copying and isn't paused.
- **Undo** is a move back through the same job, refused per task (D-048) when the task has moved on to another list or its copy has changed since (D-047's rule, by the same field comparison as verify). An unfinished move can't be undone yet.
- **CLI:** `tasks move TASK… --to LIST [--list L] [--dry-run] [--yes] [--idempotency-key K]`; several tasks need `--yes` off a terminal, as 5d's bulk changes do. **Protocol 9:** `TaskChange::Move { to }` and `TaskAction::Move`, so a client restarts an older daemon rather than have it refuse the move.
- **TUI:** `m` (and the palette's "Move to list…") on the cursor's task or the selection opens a picker of the other lists, each with its folder, ranked as the palette ranks (a folder's name finds its lists). The tasks are those on screen when `m` is pressed, so a move never reaches outside the scope; one `u` moves them back.
- **Not built, and still to be placed:** keeping a paused copy's attachment attributable (Graph has no marker for an attachment), moving a whole list, and moving tasks picked by `--overdue` or `--due-before`.

### D-053: Rung 6b, list suggestions from TypeSafe's Jev; suggest-only and opt-in; as built. (BK, rung 6b build, 2026-09-25)
- **Replaces** D-052's "6b is Jev filing a quick-added task into the right list by itself": Jev **suggests** a list and never files a task. **Amends** D-016 only for this one job: quick add stays deterministic; the model answers "which list?", nothing else, over the network rather than locally, and only when turned on.
- **Why suggest-only:** the calibration on BK's real inbox (his tasks filed since into lists, run before the build, results kept outside the repo). List names alone chose poorly. With each option described as its folder, its name and up to five of its open task titles, and a **forced choice** (no "none" option), the answers at **confidence ≥ 0.8 were right 7 times in 8** on active lists, and about 1 task in 4 reached that confidence. One wrong list in eight is fine for a hint and too many for a silent move, so the user decides.
- **Opt-in:** off unless `[suggest] enabled = true` in config.toml (D-035), with `provider = "typesafe"` (the only one), `min_confidence` (0.8), `exclude_folders` (`["Archive"]`: archived lists aren't filing targets; the calibration left them out too) and `api_key_command`. - **The key:** `TYPESAFE_API_KEY` in the daemon's environment, else `api_key_command`, run once per daemon as a process of its own, never through a shell: a string is split as a shell would split it (`shlex`, so quotes group words) or an array is the argv. The first line it prints is the key, kept in memory only, never logged, written or put in an error. A failing command is reported by its exit status only, with "no output" or "output withheld": nothing it printed, on either stream, reaches an error, the log or `doctor`. Nothing a suggestion reads (a title, a list name, TypeSafe's answer) is logged either: an unreadable answer or a choice that isn't an option is reported in general terms, without the value. The daemon reads config.toml when it starts, so a change needs `ms-todo daemon stop`. **Live finding:** `op read` run by the detached daemon didn't finish in 20 seconds (it had no way to ask for approval), so on BK's machine the key comes through `TYPESAFE_API_KEY`, set when the daemon starts.

The protocol has `SuggestList { title }`, answered `ListSuggestion { suggestion: {list_id, list_name, confidence} | null }`; an error only when suggestions are off or the title is empty. **Protocol 11.** The daemon answers `SuggestList` out of order on its connection, so a slow provider never holds up the TUI's other requests on the one connection it has.
- **The request:** `POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, `state: {task_title}`, one Choice question whose options are the candidate lists: every live list except the built-in ones (the inbox, flagged email) and those in an excluded folder, at most 255 (TypeSafe's limit), each described as `<Folder> list "<Name>". Example tasks: a; b; …` (its five newest open titles, one line each, 80 characters at most). Two lists with one name get `Name (2)`. The options are built from the cache and kept until the next sync pass finishes. The instructions are generic; the calibration's line about BK's PARA folders isn't sent, since the folder names already say it. Fewer than two candidates is no suggestion.
- **Failures are no suggestion:** no key, the network, a 4xx or 5xx, an unreadable answer, a choice that isn't an option, or the 3-second deadline (retries included). 429 and 529 are resent after 250 and 500 ms, as TypeSafe's docs ask; other statuses aren't. Each failure is warned about once in the daemon log (again only when it changes) and shown by `doctor` as `suggest: …` until a suggestion works. `doctor` also says, when enabled, what is sent: task titles, and the lists' folders, names and up to five open task titles each.

It never changes where the task goes. Rerunning a real add would add the task twice, which is why the note says move rather than the brief's "re-run". `tasks suggest-list "title"` answers in every format (`ids` is the list's ID, or nothing) for agents and scripts.

(Ctrl-l to accept)` (Tab already completes); `Ctrl-l` appends `#Finances` to the text, where it's highlighted and editable like any typed list. The hint shows only for the title it answered. An error (suggestions off, or a daemon without them) stops asking for the session; a lost connection doesn't.
- **Not built:** the palette's "Suggest lists for inbox" triage (a picker over the inbox with one suggestion per task, each a request, and a one-key move). It needs a new mode and a request per task, so it wasn't straightforward; the CLI's `suggest-list` and `tasks move` do the same job for now.

### D-056: Rung 8b, attachments; as built. (Rung 8b build, 2026-09-25)
- **Promise:** "I can attach files to a task and get them back." Reaffirms D-028 (a create with nothing to attribute it by stays `unknown` for the user), D-029 (attachments flip `hasAttachments`; metadata is fetched, S1), D-033 item 5 (downloads are a trust boundary) and D-055 (children inline, child outbox operations).
- **No `attachments` table (amends 02's draft):** an attachment's metadata (`id`, `name`, `contentType`, `size`, `lastModifiedDateTime`, never `contentBytes`) lives in the task's `raw_json` under `attachments`, a key Graph never sends inline. Present, even empty, it's what the task has; absent, it hasn't been fetched. A write of Graph's JSON without it keeps the cached list while the row is the same Graph task (`write_task`, and `carry_attachments` before later operations are laid on top). Option rejected: migration `0007` as a table, which every write path, the rollback snapshots and undo would have to keep in step with the task; inline, a child operation's local change, rollback, placeholder swap, restart rule, discard and undo work unchanged.
- **Sync:** hydration fetches `GET …/attachments` in `$batch` for each fetched task with `hasAttachments`, and sets an empty list for one without. A task needs hydrating when its etag moved or it has attachments and no list. **Migration `0007`** drops the delta link of each list holding a cached task with attachments, so the next pass reads it whole and fetches their lists. A 404 on the listing tombstones the task, as the extension's does.
- **Writes are `child` operations** on the `attachments` collection. **Add** (`action: attachment_add`): the CLI resolves each path to absolute and checks it's a regular file of 25 MB or less; the daemon checks again and records its size and modified time in the payload (`file: {path, bytes, modified}`). When sent, the file is read then and refused (`failed`, "changed after it was queued") if either differs. Under 3 MiB a POST; else an upload session. The created ID replaces the `local-…` placeholder as a step's does. **Delete** (`attachment_delete`) sends no `If-Match` (S16: ignored); a 404 is done.
- **Upload sessions (S16):** a session can't be asked where it stands, so each chunk is sent once per call, outside the HTTP client's retry, and the upload follows each answer's `nextExpectedRanges` (`"N"` or `"N-"`). A lost answer to a chunk before the last is sent again, up to 3 times with backoff, within the one attempt: 400 `InvalidStart` means it landed and the next range follows. Giving up cancels the session (a best-effort DELETE) and the operation is deferred, to start a new one. **The last PUT is the create:** a timeout or 5xx is `unknown`, flagged at once, and never sent again by itself; the ID comes from its `Location`.
- **Undo of a delete re-uploads a copy kept locally.** Before the DELETE is sent, the daemon downloads the attachment into `<data dir>/attachments-kept/` (0600, in a 0700 directory, named by a hash of the operation ID). `undo` queues an add that reads that copy, with its original name and content type; refused when the copy is gone. Copies are kept 7 days and 250 MB in all, oldest first, swept at start and after each keep. A delete whose copy can't be written deletes nothing: the operation fails ("couldn't keep a copy for undo: …; nothing was deleted") and the attachment comes back, since the user never agreed to a delete that can't be undone. `attachments delete --no-undo` keeps no copy, and its undo is refused, saying so. Undo of an add deletes the attachment, unless it's gone. Option rejected: deletes that can't be undone, confirmed only; the copy costs one download per delete and makes `u` safe as it is for everything else.
- **Downloads (D-033 item 5):** the daemon writes, the client names an absolute directory. The directory is opened **once** as a handle (`O_DIRECTORY | O_NOFOLLOW`, so a symlink is refused), and every file is made relative to it (`openat`, `linkat`, `renameat`), so a directory swapped for a link while the bytes download can't redirect a write. **`rustix`** does the at-calls: its API is safe Rust (the workspace forbids `unsafe`), it's already in the lockfile through `tempfile`, and it exposes `renameat_with(RENAME_NOREPLACE)` on Linux and macOS (`renamex_np(RENAME_EXCL)`); `cap-std` was the alternative, a whole capability filesystem API for four calls. The name loses separators, control characters and `: * ? " < > |`, leading dots and spaces, and runs of dots (so `..` can't survive); an empty result is `attachment`. The bytes go to a new 0600 `.name.<random>.part` (O_CREAT|O_EXCL, so never through a link), are synced, then take the name by a hard link, which never replaces a file (`name (1).pdf` when taken); `--force` renames over it instead, which replaces a link rather than writing through it. A filesystem without hard links gets a rename that refuses to replace, and one that can't do that either a new file made `O_EXCL` with the bytes written again: never a check then a rename. The answer gives each file's path, byte count and sha256.
- **Protocol 14:** `TaskChange::AddAttachments { files }`, `DeleteAttachments { attachments }`, `TaskAction::AttachmentAdd`/`AttachmentDelete`, and `DownloadAttachments { task, list, attachments, out_dir, force }` answered `Downloaded`, out of order like `SuggestList`, so a download never holds up the TUI's connection.
- **CLI:** `attachments list|add|download|delete`, an attachment named by its number from 1, ID or exact name, as steps are. `download` saves every attachment when none is named, into `--out` (the current directory by default). `delete` asks in a terminal and needs `--yes` elsewhere.
- **TUI:** the detail pane's **Files** under the link, each with its size (`◌` while uploading); `A` (and `a` on the Files rows) asks for a path (`~` and relative paths read from where the TUI started); Enter, `e` or `o` on a file saves it into `[attachments] download_dir` (default `~/Downloads`) and opens it with the system's opener, only if the daemon says it wrote it in that directory (`e` does what Enter does, as on a field since 0.1.23); `d` deletes after `y`. A task's row ends with `⎘` (`&` in ASCII). No Tab completion of paths: it needs directory reads in `update`, which stays free of I/O.
- **Not built:** attaching or downloading to or from anywhere but a path (stdin, a URL), a progress bar for big uploads, and resuming an upload across daemon restarts (a restart mid-upload leaves it `unknown`, as any create).

### D-059: Read UTC due dates with a local-midnight exception. (Cross-zone display fix, 2026-09-25)
- **Replaces:** D-027's nearest-local-midnight reading rule and the mapping recommendation in [S11](../research/spikes/S11.md). Due and start dates remain date-only, and a time still goes to the reminder.
- **Why:** Graph returns midnight in the writer's zone as a UTC instant but loses the writer's zone (S11). Rounding that instant in the reader's zone moves a UTC-written 25 September to the 26th for a reader in UTC+13 or UTC+14. For a UTC response, if the instant is exactly midnight in the reader's zone, use that local date; otherwise add 12 hours to the UTC instant and take its UTC date. This keeps UTC, London and Dubai-written dates stable for eastern readers while preserving dates written at midnight in UTC+13 or UTC+14 when read in the same zone. A non-UTC response requested with `Prefer: outlook.timezone` is wall time in its reported zone and is rounded as wall time, without first treating it as UTC. The CLI, TUI and Raycast extension use the same rule.
- **Limit:** the original date cannot always be reconstructed when writer and reader zones are more than 12 hours apart, because Graph no longer identifies the writer's zone. No reading rule can distinguish every such pair from the UTC instant alone.

### D-060: Reopen turns a reminder still ahead back on; a move accepts a copy with its reminder on. (Issue 005 fix, 2026-09-26)
- **Why:** Graph derives `isReminderOn` and ignores a written one (S17): writing `reminderDateTime` turns the reminder on, a transition to `completed` turns it off and keeps the time, and nothing turns it off on an open task with the time kept. Reopening sent only `status`, so the reminder stayed off, and a move of such a task always failed its check ([005](../issues/005-reminder-off-after-reopen.md)).
- **Reopen** (`tasks reopen`, the TUI toggle) of a completed task (as the cache has it) writes the task's own `reminderDateTime` (as Graph stored it) in the same PATCH as the status when that time is still ahead on this machine's clock, with `isReminderOn: true` beside it only so the cache shows it on at once. A completed task counts as off even where the cache still shows it on (a completion not yet sent). A reminder whose time has passed stays off: turning it on would fire a stale reminder at once. Option rejected: turning it on whatever the time.
- **Completion** of a task that isn't repeating adds `isReminderOn: false` when its reminder is on. Graph ignores it and turns the reminder off anyway (S17); it's there so the cache, and every undo record taken before Graph answers, shows the reminder off as Graph will. A repeating task is left alone: Graph rolls it on with its reminder on.
- **Undo of a completion** does the same when the task's state before the completion (the operation's rollback record) had the reminder on and its time hasn't changed since, whether the time is ahead or not: undo puts back what was. **Undo of a reopen** sends the time back only if the reminder was on before the reopen, since a time written with the completion turns the reminder on (S17). An open task is never given its time again by a reopen, so undo can always put it back.
- **Move:** the copy is created with the time, as before, and Graph turns its reminder on. The check expects the copy's reminder on when the source's is off with a time, and compares that with the copy's actual flag; undo's changed-since check compares actual flags. The cache takes the copy's value. For a completed task or a past time this changes nothing that fires; an open task with a future time and its reminder off (only the app's reopen leaves one) gets its reminder back on, which matches the reopen rule. Options rejected: leaving the time out of the copy (loses it), and completing the copy twice to turn it off (rolls a repeating task forward).

- **Opt-in, by config:** `[search] semantic = true` in config.toml turns it on, read when the daemon starts. Off (the default), `search --semantic` exits 2 with how to turn it on and what that downloads, and nothing touches the network. Option rejected: turning it on at the first `--semantic` after a confirmation line, which an agent or a script can't answer, and which would make a download the side effect of a search.
- **First use:** with it on, the daemon downloads the model's three files into `models/potion-base-8M-bf8b056/` in the instance's data directory, each from its pinned `resolve/<commit>/` URL and checked against a pinned SHA-256 before it's kept (written as `.part`, then renamed; a download larger than the pinned size stops). Every load checks the files again, and downloads one afresh when it doesn't match. A failed load is retried by the next search, or by the indexer after 5 minutes. Debug builds can read a ready model from `MS_TODO_SEMANTIC_MODEL_DIR` instead, for tests; release builds ignore it.
- **The index:** migration `0008` adds `task_embeddings` (a task's vector as little-endian f32s, unit length, with the model's ID and the SHA-256 of the text it was made from). The text is the one FTS indexes: the title, then the plain-text notes. The daemon's indexer embeds every live task whose hash or model differs, in batches of 256 off the async threads, when the model loads and then after each change to the cache (it follows the same events clients subscribe to, and lets a sync pass's changes gather for a second). It drops the vectors of tombstoned tasks and of other models. Steps and attachments aren't searched.
- **The query:** the query's vector against every candidate's by cosine similarity, brute force (under a millisecond for a few thousand; no sqlite-vec), best first, with `--list`, `--status` and `--limit` as keyword search has them. Results under 0.15 are dropped, so a search is a short list rather than every task in order. Each result is the task with `list` and `score` (to three places) instead of `snippet`, and the answer says how many tasks in scope aren't embedded for their current text yet (`semantic.pending` in JSON, a note on stderr otherwise): they're missing, or ranked by their old text. A CLI search waits for the model while it loads, and the model's first indexing pass runs before any waiting search gets it. **Hybrid ranking isn't built:** the set's keyword queries already came first by meaning alone.
- **TUI:** `Ctrl-s` in the `/` filter switches it to meaning (the prompt and the list's title show `~` for `/`) and back; the text is sent as typed, not as a prefix search. The TUI's request never waits for the model: while it's off, loading or failing, the reason shows under the filter and the last results stay. The daemon sends a new subscription event, `IndexChanged`, when the model finishes loading and after a pass that embedded tasks, and the TUI re-runs a filter by meaning on it, so it never keeps results ranked by old text or a "not ready" reason once the model is up (older clients skip the event).
- **With rung 9a (D-061):** a search by meaning, like a keyword search, includes deferred and Someday tasks, and the table marks them `(deferred to …)` or `(someday)`; JSON has `defer_until` and `someday` on every item. The TUI's semantic filter follows the same rule as its `/` filter, including in Next.
- **Protocol 18:** `SearchTasks.semantic` and `Seed.semantic`, so an older daemon never answers a search by meaning with a keyword search; `SearchResults.semantic` and `DoctorReport.semantic` (state `off`, `loading`, `ready` or `failed`, the model, where it's kept, the download size, and how many tasks are indexed and pending).

### D-063: Rung 9b, nag reminders as local notifications; as built. (BK, rung 9b build, 2026-09-27)

Linux: no notifier yet, and `doctor` says so. `notify-rust` would reach D-Bus there, but S18 ruled it out on the machine that matters, and nobody could test it.
- **`doctor --notify-test`** shows one notification through the same path, then the usual report; it's a flag, not a `nag test` command, to keep the surface small. `doctor` has `nag` (`active`, `notifier`, `quiet_hours`, `count`, `problem`).

- **Protocol 19:** `NewTask.nag`, `TaskEdit.nag`, `TaskFilter.nagging`, `NotifyTest` and `DoctorReport.nag`. No migration: `settings` from `0006` holds the last-nagged times.
- **Not built:** moving the reminder on the server, nags on the phone, snooze, notification actions (non-goals); nags on Linux.
- **Deferred and Someday tasks don't nag** (9a's rule, D-061): a task out of the everyday views waits until it shows again, then nags as usual.
- **Setting or stopping a nag** forgets when that task last nagged, so a nag turned off and on again (between two ticks, or in quiet hours, which skip the tick's pruning) nags as soon as its reminder has passed, not an interval later.
- **Known limits, accepted:** a restart in the middle of a batch of notifications may show one again; in the hour when the clocks go back, a reminder in that hour may start its nag an hour early (its earlier reading is taken); a clock corrected backwards pauses nags until it passes the saved last-nagged time.

### D-065: Closing the placed-later gaps (daemon); as built. (BK's list, 2026-09-27)
- **Closes** what D-038, D-040, D-043 and D-063 left "not built, and still to be placed" on the daemon's side: pruning the outbox, `outbox.unknown_lookup_hours`, `ConflictOverwritten`, the TUI focus hint, starting the daemon at login, nags on Linux, and the TUI starting a daemon that went away. **Replaces** D-040's "keeps rung 2's conflict rule, instead of 04's last write wins" for task edits: 04's policy is now built as written.
- **Pruning** (`crates/store/src/outbox/prune.rs`, `crates/daemon/src/outbox/prune.rs`): when the daemon starts (before it listens) and once a day, a command whose operations are all `done` and finished more than `[outbox] retention_days` ago (default 30) is deleted. A discarded operation was already deleted when discarded; `failed` and unresolved ones wait for the user. Two rules keep what's left sound: an operation some unfinished one depends on stays (the worker sends an operation only once its dependency is `done`, so a retried `failed` one would wait for ever), a command and its undo go together or not at all (with the undo gone, `undo` would offer the command again), and a command an `--idempotency-key` still answers for stays until the key expires, then goes with the key's record. **`undo` has no lookback of its own**, so the window is how far back it reaches; past it, `undo OP_ID` is `not_found`. At least 1 day, so an `--idempotency-key` still replays for its 24 hours. `doctor` has `outbox_upkeep`: `rows`, both settings, when the last prune ran and what it removed. Option rejected: pruning by row, which splits a command's operations and undo pairs.

Step and link writes keep D-055's rule. Why now: the note and the undo make an overwrite visible and reversible, which a `failed` write the user must retry by hand never was.

The TUI sends it with the seed whenever the sidebar opens a list or view. Option rejected: reading focus from `Seed`, which the TUI also sends to read views ahead.

A crash restarts it; `daemon stop`, and a second daemon that finds the lock taken, exit 0 and don't. The installing shell's `MS_TODO_CONFIG_DIR`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_RUNTIME_DIR`, those set, go into the service's environment (`EnvironmentVariables`, `Environment=`) and the answer's `environment`, so the daemon at login reads the same config and data. `daemon uninstall` removes both files. Both are idempotent (`changed` says whether anything was), refuse any instance but the default (exit 2), and **only write files**: no `launchctl` or `systemctl`, so a test with its own HOME changes nothing else and the running session is untouched; the answer's `now` gives the command to start (or stop) it now. `doctor` has `service` (`installed`, `manager`, `path`) and, on the default instance, a problem when tasks nag and it isn't installed.

### D-067: Closing the move, attachment and task-link gaps. (BK's gap list, build of 2026-09-27)
- **Replaces** the "not built" items of D-051 (moving a whole list, moving tasks picked by `--overdue` or `--due-before`) and of D-056 (attaching from stdin or a URL, a progress bar, resuming an upload across a daemon restart). Reaffirms D-019 and D-028: every task still moves through D-051's verified job, and nothing that may have committed is sent again by itself.
- **`tasks move` takes a selection:** `--overdue`, `--due-before W` and `--folder F` pick open tasks as `reschedule` and `tasks edit` do (`TaskSelect`, resolved in the daemon when the change runs, narrowed by the context as D-064 says), previewed and confirmed as 5d's bulk changes are, one operation per task under one `op_id`. - **`lists merge FROM --into TO [--include-completed] [--delete-source]`**, the name chosen as the clearest (the blueprint named none; `lists move` already means folders). It queues one D-051 move per open task (completed ones with `--include-completed`) under one `op_id`, so one `undo` moves them all back, and a crash resumes each move as any move resumes. The TUI's palette has "Merge list into…", which never deletes the source. **`--delete-source`** queues the list's delete as its own command, `<op_id>.delete`, with no local change until it's sent: it's ready only once no operation of the merge is unresolved (`after_command`, checked in `ready_ops`), and it's sent only if every move is `done`, the cache holds no task in the list and Microsoft To Do lists none; otherwise it's rejected and the list kept. A list holding completed tasks needs `--include-completed` with it (exit 2), and a built-in list can't be deleted. Undoing the moves while the delete still waits drops the delete in the same transaction, so it can never run before the moves back; while it's being sent, the undo is refused until it's done.
- **Attachments from stdin and URLs keep "no bytes cross the socket."** `attachments add T - --name N`: the CLI saves stdin (25 MB at most, not empty, not a terminal) to a new 0600 temporary file and sends its path with `copy`; the daemon copies it into `attachments-staged/` in its data directory before answering, and the CLI removes its file. `attachments add T https://…`: the **daemon** downloads it (the process that owns the network; the CLI stays free of HTTP) into the same directory, `https` only, following at most 5 redirects and only to `https`, never to this machine or its network (loopback, private, link-local, unique-local, site-local, shared: checked in the resolver the connection uses, so there's no gap for a name to resolve differently, and before each hop for an address written in the URL; redirects are followed by hand with a second client, so only the first request may reach the host the user typed, never a redirect back to it; no proxy is used, since a proxy would resolve names past the check), stopping past 25 MB whatever the server announced; the name is `--name`, else the URL's last path segment, and the type is guessed from the name, else the server's. A dry run downloads nothing. The staged copy is what the outbox reads, so an upload, a resend after a restart or `outbox retry` reads bytes that can't change; it's removed once the add is sent, and a sweep when the daemon starts removes any that no unfinished operation reads (older than 10 minutes); one an unfinished operation reads is never removed, whatever its age. Option rejected: the CLI downloading into a temporary file, which would put HTTP in the CLI and leave the file's life to a process that exits.
- **Upload progress** is an event, `UploadProgress { op_id, task_id, name, sent, total, done }`, sent to subscribers as a session starts, after each chunk, and once when the attempt ends (`done`, finished or not). In a terminal, `attachments add` subscribes before sending and draws one line on stderr (`Uploading scan.bin: 6.6 MB of 12.0 MB (54%)`) for the uploads it queued that go through a session; it stops watching after 15 seconds with no start or 2 minutes with no progress, and Ctrl-C stops only the watching. The TUI shows a gauge in its status line.
- **Resuming an upload (S16, D-056):** before each PUT, the session's URL, the next byte and whether the PUT is the final one are saved in the operation's `progress_json` (an `UploadWatcher` in `ms-todo-graph`). A daemon that stops mid-upload leaves the operation `pending`, not `unknown`, unless the final PUT, the only one that commits, may have gone; that one is `unknown` and flagged as before. Resumed, the upload sends again from the saved byte: Graph's `InvalidStart` says that chunk landed. A session that refuses the first PUT (expired after 2 hours, or gone) is left, cancelled best-effort, and a new one started from the start: nothing uncommitted can make an attachment, so there's never a second. A definite failure clears the saved session; `outbox retry` starts afresh. The saved URL carries its own short-lived authorisation and stays in the local database, never in `outbox list`.

Each operation is a change to a set (`link: { other, linked, stale }` in its payload), made on Graph's list when it's sent, so a link another device made meanwhile is kept; `undo` does the opposite to that one ID on both tasks as they are now, so undoing `relate A B` after `relate A C` leaves A–C and never leaves a link one-way. Option rejected: restoring each side's whole array, which a later link to a third task refused on one side only. Graph IDs so another machine's ms-todo can follow them; a task moved by this machine has a new one, and a link by the old ID still finds it through the finished move (`moved_from`), and linking again brings it up to date. A task Graph doesn't have yet is refused. `tasks show` and the TUI's seed carry `related: [{ id, graph_id, title, list_id, status }]`, fields null for a task this cache doesn't have; the detail pane lists them and Enter opens one in its list. **Found live (S21):** Graph refuses an array in an open extension without `related@odata.type: "#Collection(String)"`; every extension write now tags a non-empty array of strings that has no type with one (ours, and `extensions set`'s), keeps the type annotations Graph has for fields it doesn't write anew (and `extensions delete`'s undo snapshot keeps them, so a typed array comes back) (`scores@odata.type: "#Collection(Int64)"` survives a My Day write), and the fake Graph refuses an untyped array.
- **Found live, fixed here:** a moved task's copy was cached without its attachments' metadata, so `attachments list` showed none until the copy's etag moved; the check that downloads the copy's attachments now records their listing with it.

### D-069: A due date on a recurring task is written without splitting it. (Issue 007 fix, 2026-09-27)
- **Why:** Graph answers a PATCH that sets `dueDateTime` on a recurring task by moving the series on and creating a new open recurring task with that date (S20). Undoing a recurring completion, `tasks edit --due`, `reschedule` and their undos all left two tasks. Clearing a recurring task's date (My Day's removal) dropped its recurrence.
- **In the outbox, for every such PATCH** (`crates/daemon/src/outbox/series.rs`): when a task update sets a due date on a task that recurs, and doesn't set the recurrence itself, it's sent as two PATCHes in one operation: the body with `recurrence: null`, then the recurrence as cached with `range.startDate` moved to the new date's day. One operation, so one undo. **The recurrence is Graph's, read first,** not the cache's, so one another device changed meanwhile is kept (the 412 and conflict rules judge only the operation's own body, the date). **It's kept in the operation** (`series` in the payload) before the first PATCH: a retry that finds the date there and no recurrence (the second PATCH refused, or the daemon stopped between them) sets it from the operation, and a 412 on the second PATCH (another device, or the HTTP client's retry after a lost answer) reads the task and counts one already holding it as done. **Where the date landed** is kept too (`landed`) when Graph moved it to the pattern's next day, and undo's changed-since check compares that, not the date asked for. Found live: the date and recurrence in one PATCH still split it, and with the old start Graph moves the task back to it. A date off the pattern (a Wednesday for a Sunday task) goes to the next occurrence, as the pattern says.
- **Replaces** 04's "restoring the old due date" for undoing a recurring completion only in how it's sent: undo still queues the copy's delete and one due-date edit.
- **My Day leaves a recurring task's due date alone:** adding it to a later My Day doesn't move a date ms-todo set, and taking it out (or the rollover) doesn't clear it; `myDayDueSet` is dropped, as for a date the user set. Option rejected: moving it through the fix above, which would move the whole series each day.
- **Left:** if the second PATCH is rejected for good, the task is left without its recurrence until `outbox retry`, which sets it from the operation; the operation is `failed` in `outbox list` meanwhile. `tasks edit --clear-due` on a recurring task still drops the recurrence, which is what Graph does with a task without a date.

### D-070: Closing the open issues: extension races, the move's delete, context edge cases. (BK: close every open issue, 2026-09-28)
- **Issue 001, extension write races, decided by a spike** (S2's follow-up): an extension has no etag of its own; a task's extension PATCH, POST and DELETE honour `If-Match` with the **task's** etag, a list's ignore it (as list PATCH does). So a task's extension write (`myDay`, `assignee`, `related` and their flags) sends `If-Match` with the etag of the GET it merged into, and on a 412 reads, merges and writes again, 3 times at most in one attempt, then waits for the next round (`conflict`, temporary). A list's extension write (`folder`, `order`, `folderOrder`) can't be conditional: the residual window is the one round trip between our GET and our PATCH. After writing, it reads the list again, and a field not as written gets a note on the operation and a `ConflictOverwritten` event. Option rejected: reading the list again right before the PATCH, since the GET and PATCH are already back to back, so it wouldn't narrow anything. Options not taken: one extension per field group (a migration of every document for a window the spike closed on tasks).
- **Issue 004, the move's delete:** its second option (look for the edit in the final delta round) can't work: a delta round reports an edited-then-deleted task as a bare `@removed`, with no timestamp (S6's follow-up). The source is now deleted by a `$batch` of an empty `PATCH` with `If-Match` (the verified etag) and the `DELETE` with `dependsOn` it: a source changed meanwhile is a 412, Graph never runs the DELETE, and the move pauses with both kept, as for a change the last read sees. The last read stays. What's left is the gap between the batch's two steps inside Graph. A resent batch after only its PATCH landed reads as changed and pauses (safe: nothing deleted). `GraphClient::delete_task_if_unchanged`; the fake Graph's `$batch` now runs a task's PATCH and DELETE steps.
- **Issue 006, context edge cases:** the fingerprint of `AddTask` and `ChangeTasks` covers the context they're resolved in, active or `--context` (name and list IDs), so an `--idempotency-key` reused after `ctx` or an edit of the context's lists exits 2. The TUI leaves a context whose lists changed as it leaves a switched one (replaces D-064's second known gap). Semantic `pending` counts the context's lists only. `ctx list --format ids` prints names; `ctx` with none active shows the configured contexts' problems.
- **Review findings, checked with tests:** a move queued after an edit of its task waits on that edit; when another device deleted the task's list, the edit failed but the move waited for ever. Failing a deleted list's operations now fails what waits on them too (`fail_ops_in_list` cascades). A move with nothing to wait on already failed at its next attempt. The TUI's fallback from a deleted list left that list's rows actionable until the default seed came back; they're cleared now.
- No protocol change and no migration.

### D-071: Reliability boundaries apply before sending and when recording outcomes. (BK: implement the codebase audit, 2026-09-29)
- **One completion per observed occurrence:** the TUI holds completion/reopen actions pending per task until their reply. The store checks within the enqueue transaction, so concurrent clients cannot queue a second completion for the same recurring due date. Before sending a recurring completion, and after a 412, the outbox checks Graph's date against the operation's `due_before`. A moved occurrence remains a `conflict` (D-040); an intentional completion after the first settles can finish the next occurrence. Unknown outcomes are still never replayed automatically.
- **A skipped write is recorded whole:** the fetched task, completed outbox state and `skipped:` reason commit together. A persistence failure rolls back all three, so dependent ownership flags and undo cannot mistake a skipped write for one ms-todo applied.
- **Hydration failure does not advance its etag:** if the outer attachment batch fails, its affected tasks remain unhydrated, as on a per-item failure. A replay can recover attachment metadata and its filename search entry without another remote edit.
- **Bound TUI stalls:** Subscribe has a 3-second acknowledgement/send deadline. Pending requests and their sends have a 300-second stall deadline, extended only by traffic for that request. Idle subscriptions have no deadline; reconnecting resubscribes and refreshes without replaying writes. Interrupted writes retain the uncertain-outcome guidance.
- **Keep authorization out of diagnostics:** reqwest errors lose their URL before classification or rendering, and rejected pagination links are not interpolated into errors (D-067). Error kinds and retry decisions stay intact.
- **Raycast follows the CLI contract:** Search explicitly includes deferred and Someday tasks and labels them (D-061); Browse keeps its normal filtering. Capture puts flags before `--` and text after it; rename sends `--title=<value>` so a leading hyphen stays title content.
- No protocol change, migration or new product feature. These repair the existing decisions rather than replace them. Regression tests and the shared local/CI check command are recorded in [the implementation handover](../../plans/README.md).
