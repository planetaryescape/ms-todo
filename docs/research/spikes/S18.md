# S18: can a detached daemon show a macOS notification?

Run: 2026-09-27, macOS 27.0 (26A428), Apple silicon, from a scratch crate outside the repo. No Microsoft data was involved.

Asked for rung 9b (nag reminders): the daemon runs detached (`setsid`, parent launchd, no terminal, no app bundle, D-046). Can it put a notification on screen, and with what?

## Answer

**A library can't; `osascript` can.** `notify-rust` 4.18 (through `mac-notification-sys`) returns `Ok(())` and nothing appears: `usernoted` refuses it. `osascript`'s `display notification` is delivered and presented as a banner, from a terminal and from a detached process alike.

| Sender | Where from | `show()` / exit | `usernoted` says | Shown |
|---|---|---|---|---|
| `notify-rust` 4.18.1 | a terminal | `Ok(())` | `Legacy client com.apple.finder connecting to modern client. You can't mix modern clients with legacy clients.` then `Denying message 3 from connection <LegacyConnection identifier: com.apple.Finder …>` | no |
| `notify-rust` 4.18.1 | detached: spawn, `setsid`, spawn again, as the daemon's launch does | `Ok(())` | the same denial | no |
| `/usr/bin/osascript` with argv | a terminal | exit 0 | `Connection com.apple.ScriptEditor2 with path: /usr/bin/osascript` … `Delivering … to [ .alert .lockScreen .notificationCenter ]` … `Presenting … as banner` | yes |
| `/usr/bin/osascript` with argv | detached, as above | exit 0 | the same delivery and `Presenting … as banner` | yes |

`mac-notification-sys` posts through the deprecated `NSUserNotificationCenter`, borrowing Finder's bundle ID when the process has none. macOS 27 denies that legacy path for a bundle that's a modern (`UNUserNotificationCenter`) client, and the library doesn't see the denial, so the failure is silent. A process without a bundle can't use `UNUserNotificationCenter` at all, so no Rust library fixes this short of shipping ms-todo as an app bundle.

`osascript` is Apple's own signed tool. Its notifications are attributed to Script Editor (`com.apple.ScriptEditor2`), so they follow Script Editor's setting in System Settings > Notifications; if that's off, `osascript` still exits 0 and nothing shows.

## How it was checked

- The notification's fate was read from the unified log rather than the screen: `/usr/bin/log show --last 2m --style compact --predicate 'process == "usernoted"'` (zsh's own `log` builtin shadows `/usr/bin/log`).
- The title was passed as data, never as script text: `osascript -e 'on run argv' -e 'display notification (item 2 of argv) with title (item 1 of argv)' -e 'end run' -- TITLE BODY`. A title holding `"`, `&` and `$(x)` came through as typed.

## What ms-todo does with it

- macOS: the daemon runs `/usr/bin/osascript` with the task's title and list as argv, with no shell (D-063).
- Linux: not built. `notify-rust` would reach D-Bus there, but it was the library this spike ruled out on the platform that matters here, and it pulls in `zbus` for a path nobody has tested. `doctor` says nagging isn't available on this system.
- `doctor --notify-test` sends one notification through the same path, so a user can check Script Editor's setting.
