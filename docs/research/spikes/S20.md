# S20: a due-date PATCH on a recurring task, and a new task's etag

Run: 2026-09-27 19:55–19:59 UTC (a Sunday; 20:55–20:59 in London), on the `livetest` instance, in the throwaway list `ms-todo-spike-g1-2055` (deleted afterwards). Found while checking the undo picker live for D-065; ms-todo's release build and `ms-todo raw`. Task IDs shortened to their last characters.

## Answer

1. **A PATCH of `dueDateTime` on a recurring task doesn't move that task.** Graph leaves the task ID with the series, moves it on (to 00:00 UTC of the next occurrence's day), and **creates a new task** (new ID, new `createdDateTime`, `notStarted`, `recurrence` still set) with the due date asked for. Seen three times: undo of a recurring completion sending the old due date back (a day earlier), and two direct PATCHes, one to an earlier day and one to a later one. Confidence: high for what happens; the rule behind it (an "occurrence moved" exception?) is unknown.
2. **A new recurring task changes on Graph within a second of its 201.** Its etag moves and its `dueDateTime` is written back in UTC (`2026-09-26T23:00Z` for the `2026-09-27T00:00 Europe/London` sent). A completion sent before the next sync saw it gets a 412, and a comparison of the raw JSON reads the date as changed on another device. Confidence: high (seen once, explained by the rows).

## Part 3: every path that moves a due date (2026-09-27, 20:46–21:05 UTC)

In the throwaway list `ms-todo-spike-007b-2146` (deleted afterwards), with ms-todo's release build before the fix:

- `tasks edit <daily> --due tue` and `reschedule --overdue --to wed` **split** the task (a new recurring task on the day asked for, the series left behind).
- My Day's due date: `myday remove` on a task made recurring after My Day set its date sent `dueDateTime: null`, and Graph **dropped the recurrence** with the date. (Adding it to a later My Day would move that date, and split it like an edit.)

**The recurrence's `range.startDate` must move with the date.** Sequence C with the old start (09-27) and a new date after it (09-30) put the task back on the 27th; with the start moved to the 30th it stayed on the 30th. A weekly (Sunday) task given a Wednesday moved to the next Sunday, its start with it: a date off the pattern goes to the next occurrence.

With the fix (D-069: every PATCH that sets a due date on a recurring task is sent as sequence C, the start moved to the new day; My Day leaves a recurring task's date alone), in the same list: `tasks edit --due wed` left one task on the 30th starting the 30th, and its `undo` put it back on the 27th; `reschedule --overdue --to thu` left one task on 1 Oct; a weekly (Sunday) task edited to 11 Oct left one task on 11 Oct; undoing a completion left one task on its day; `myday remove` on the recurring task kept its date and recurrence. Every operation was `done`.

After the review of b58f9fe (list `ms-todo-spike-007c-*`, deleted): a weekly (Sunday) task edited to Wednesday 30 September landed on Sunday 4 October, one task, starting that day; `undo` of the edit was accepted (it compares where the date landed) and put it back on 27 September, one task.

## What it changes

- Every due-date write to a recurring task (undoing a completion, `tasks edit --due`, `reschedule`, the undo of either) split it. Fixed by sequence C with the start moved, in the outbox (D-069); My Day no longer moves or clears a recurring task's date. [Issue 007](../../issues/007-recurring-due-date-patch-splits.md).
- Comparing a task's fields across a 412 must read dates as dates (D-065).
