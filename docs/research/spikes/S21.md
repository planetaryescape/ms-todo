# S21: can an open extension hold an array?

Run: 2026-09-27 21:05–21:08 BST, BK's personal MSA, Graph v1.0, one task in the throwaway list `ms-todo-spike-g3-2104` on the `livetestg3` instance. IDs are shortened; auth headers were sent and aren't shown. The task's extension was put back as it was, and the list deleted after the run.

Asked for D-067: related tasks keep the other task's Graph ID in ms-todo's extension as `related: [ids]`. The fake Graph took the array; the first live `tasks relate` didn't.

## Answer

**Only with its type beside it.** A PATCH of the extension with `"related": ["…"]` alone is **400 `invalidRequest`**: `The given untyped value '["…"]' in payload is invalid. Consider using a OData type annotation explicitly.` The same PATCH with `"related@odata.type": "#Collection(String)"` beside it is 200, and a GET, bare or through the task's filtered `$expand`, gives both keys back. Confidence: high.

| Request | Status |
|---|---|
| `PATCH …/tasks/{T}/extensions/com.planetaryescape.mstodo` `{ opId, related: ["…"] }` (ms-todo's first `relate`) | 400 `invalidRequest`, untyped value |
| the same with `"related@odata.type": "#Collection(String)"` | 200 |
| `GET …/extensions/com.planetaryescape.mstodo` | 200, `related` and `related@odata.type` |
| `GET …/tasks/{T}?$expand=extensions($filter=id eq '…')` | 200, the same in `extensions[0]` |
| `PATCH` `{ opId }` alone (putting it back) | 200 |

## What ms-todo does with it

- Every write of our extension (the `task_extension` and folder writes, a task's create, a move's copy) sends `<field>@odata.type: "#Collection(String)"` beside each array it holds; annotations read back are dropped and written afresh, as integers' `@odata.type` already were (D-047).
- The fake Graph now answers an untyped array in an extension write with this 400, so a test catches a write that forgets it.
