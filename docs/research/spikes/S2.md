# S2: do lists/delta and tasks/delta report open-extension changes? Does $expand=extensions work?

Run: 2026-09-24 14:13–14:15 UTC. Throwaway list `{L}` (see S1), task "S2 extension task". Extension name `com.planetaryescape.mstodo`.
Auth header redacted everywhere.

## Answer

- **Change detection: yes.** Creating, PATCHing or deleting an open extension bumps the parent's `@odata.etag` (and for tasks
  `lastModifiedDateTime`), and the parent appears in the next `tasks/delta` / `lists/delta` round. Confidence: high.
- **Content via delta: no.** Delta never returns extension data. `$expand=extensions` is accepted (200) but silently returns nothing;
  `$expand=extensions($filter=id eq '…')` on delta is a **400**. Confidence: high.
- **Content via plain GET / list: yes, but only with a filtered expand.** `$expand=extensions` alone returns nothing (silently);
  `$expand=extensions($filter=id eq 'com.planetaryescape.mstodo')` works on single GET and on collection GET, for lists and tasks.
  It also combines with `$filter=lastModifiedDateTime ge …` and `$orderby`/`$top`.

## Conclusion

Extension changes are *detected* by delta (etag/lastModified bump), but their *content* has to be fetched separately. Two cheap ways:

- Lists: after every `lists/delta` round that reports any list, one `GET /me/todo/lists?$expand=extensions($filter=id eq 'com.planetaryescape.mstodo')` (one request for all ~30 lists).
- Tasks: for tasks reported by delta, `GET /me/todo/lists/{l}/tasks?$filter=lastModifiedDateTime ge {since}&$expand=extensions($filter=id eq '…')`
  (one request per changed list), or `$batch` of per-task GETs with the same filtered expand.

Writes: extension PATCH is a full replace, so always send the whole document (or POST it, which upserts). Confidence: high.

## Follow-up: does an extension write honour `If-Match`? (2026-09-27, issue 001)

Run: 2026-09-27 21:22–21:25 UTC, `livetestg5` instance, throwaway list `ms-todo-spike-g5-2222` (deleted afterwards), one task with our extension. Auth header redacted.

**Answer: on a task, yes, by the task's etag; on a list, no.** Confidence: high.

- The extension has **no `@odata.etag` of its own**: neither `GET …/extensions/{name}` nor the `$expand` carries one. The only etag is the parent's.
- **Task extensions:** `PATCH`, `POST` (upsert) and `DELETE` of `…/tasks/{T}/extensions/{name}` with `If-Match: <the task's @odata.etag>` are conditional. A stale etag is **412** `ErrorIrresolvableConflict` and nothing is written; the current one is 200/201/204. Since every extension write moves the task's etag (above), a concurrent write by another device to *another field* of the extension makes ours 412, which is the case issue 001 is about. An edit of the task's own fields moves the etag too, so it 412s as well (harmless: read again and write).
- **List extensions:** `If-Match` is **ignored**. `PATCH`, `POST` and `DELETE` of `…/lists/{L}/extensions/{name}` with a stale list etag all succeeded (200, 201, 204) and wrote. A plain `PATCH /me/todo/lists/{L}` with a stale etag is also 200: lists don't honour `If-Match` at all.
- A malformed `If-Match` (`W/"bogus"`) or `*` is **500** `generalException` on both, and writes nothing. The etag without its `W/` prefix is accepted.

| Request | If-Match | Status | Result |
|---|---|---|---|
| `PATCH …/tasks/{T}/extensions/{name}` | `W/"bogus"` | 500 | unchanged |
| same | stale task etag | **412** | unchanged |
| same | `*` | 500 | unchanged |
| same | current task etag | 200 | written; task etag moved |
| another client `PATCH`es field `b` (no If-Match), then ours with the etag read before it | older task etag | **412** | `b` kept |
| `POST …/tasks/{T}/extensions` (upsert) | stale task etag | **412** | unchanged |
| `DELETE …/tasks/{T}/extensions/{name}` | stale task etag | **412** | unchanged |
| `POST …/lists/{L}/extensions` | current list etag | 201 | written |
| `PATCH …/lists/{L}/extensions/{name}` | stale list etag | **200** | written |
| `POST …/lists/{L}/extensions` | stale list etag | **201** | written |
| `DELETE …/lists/{L}/extensions/{name}` | stale list etag | **204** | deleted |
| `PATCH …/lists/{L}/extensions/{name}` | `W/"bogus"` | 500 | unchanged |
| `PATCH /me/todo/lists/{L}` (displayName) | stale list etag | **200** | written |

**Conclusion (D-070):** a task's extension write sends `If-Match` with the task's etag from the GET it merged into, and on a 412 reads, merges and writes again (bounded). A list's extension write can't be conditional: it reads again right before the write, merges again if a field it isn't writing moved, and reads once more after, noting a field it didn't write that changed in the gap.
