# S16: how does an upload session resume, and what does an attachment look like?

Run: 2026-09-25 08:04–08:10 UTC, BK's personal MSA, Graph v1.0, one task in the throwaway list `ms-todo-spike-2026-09-24` (`{L}`, task `{T}`: "S13 plain control"). IDs are redacted; auth headers were sent and aren't shown. Every attachment made was deleted after the run, and the task is back to none.

Asked for rung 8b (D-056): 03 says to resume an interrupted upload with `nextExpectedRanges`, and 04 that a lost answer to the final PUT is `unknown`. How does a session say where it stands, what happens to a chunk sent twice, and how does the final PUT name what it made?

## Answer

**A session can't be asked where it stands; only each PUT's answer says.** A GET of the `uploadUrl`, bare or with `/content`, is 404 `UnknownError`, before and after a chunk. So an upload resumes from the answers it gets:

- Each PUT but the last answers 200 with `nextExpectedRanges: ["3276800"]`: the next start, **without the trailing dash** the Graph docs show (the session's create does say `["0-"]`).
- A PUT of a range the session already has is **400 `invalidRequest`, inner code `InvalidStart`**, and the session carries on: the right next chunk then succeeds. So a chunk whose answer was lost can be sent again; `InvalidStart` means it landed.
- A PUT that skips ahead is refused too: one that skipped to the last range got a **504 after 29 seconds** and committed nothing (the session then finished normally from where it was).
- The last PUT answers 201, no body, and `Location` is the new attachment's whole URL: `https://graph.microsoft.com/v1.0/users/<address>/todo/lists/{L}/tasks/{T}/attachments/{id}`.

Confidence: high for what was seen; a status endpoint Microsoft documents elsewhere isn't there for To Do.

Also seen:

- `GET …/attachments` lists `@odata.type`, `id`, `name`, `contentType`, `size`, `lastModifiedDateTime`, **never `contentBytes`**, and `$select` of those fields is accepted. `size` is the file's bytes plus about 240 (7,352,377 bytes → 7,352,614), as S14 found.
- A direct POST's 201 **echoes `contentBytes`** in its answer, and has a `Location` too.
- **An attachment DELETE ignores `If-Match`:** with the task's etag from before the attachment was added (stale), it's 204. A second DELETE is 404 `ErrorItemNotFound`.
- Graph keeps any name: a file named `s16 ../weird:name?.txt` was stored and listed as that.
- Every attachment write moves the task's etag and sets `hasAttachments` (S1).

## Conclusion

- Send every chunk once per attempt, never through the HTTP client's own retry, so the upload knows which PUT may have landed. After a lost answer to one that isn't the last, send it again: 200 goes on from its `nextExpectedRanges`, 400 `InvalidStart` means it landed and goes on from the next range. Give up after a few, and the operation tries again later with a new session.
- The last PUT is the create: a lost answer is `unknown`, never sent again (04).
- Read `nextExpectedRanges` in both shapes, `"N"` and `"N-"`.
- Take the attachment's ID from the last PUT's `Location`, after its last `/attachments/`.
- Keep only the metadata fields; never cache `contentBytes`.
- Send no `If-Match` on an attachment DELETE, and count its 404 as done.
- Treat a name from Graph as untrusted when it names a file (D-033 item 5).
