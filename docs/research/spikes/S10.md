## Answer

`$batch` works for To Do GETs and writes (POST task, PATCH task, POST checklistItem, GET with filtered `$expand`, delta).
Constraints found:

1. **Max 20 requests.** 21 → top-level **400** "Number of requests inside batch exceed the limit."
2. **A batch must be fully sequential or fully parallel.** Mixing (e.g. four independent `dependsOn` chains) → top-level **400**
   "Batch should be either fully sequential or fully parallel". So "4 parallel chains of 5" is impossible.
3. **Parallel batches run their sub-requests concurrently and hit the 4-concurrent limit**: 20 parallel GETs → 9×200 + 11×429
   (Retry-After 2–10 s); a second run similar. A 7-request mixed batch → 1×429 (on the PATCH). The outer response is still **200**.
4. **Fully sequential (`dependsOn` chain) batches of 20 never throttled**: 20 GETs → 20×200; six 20-POST batches → 120×201,
   3.3–5.8 s per batch (~170–290 ms per write).
5. In a chain, a failed step makes every later step **424** `FailedDependency` "Request failed as dependent request failed".
6. Sub-responses carry their own headers (`ETag`, `Retry-After`, `Location`); `ETag` equals the body's `@odata.etag`.
7. A malformed id in a sub-request → sub-status 400 `ErrorInvalidIdMalformed` (not 404).

## Conclusion

- Use **sequential** batches (`dependsOn` chain, ≤20) for bulk writes and fan-out reads: they save round trips (~1 HTTP request per 20
  operations) without adding concurrency. Use parallel batches only with ≤4 sub-requests, and only if nothing else is in flight.
- A failed step in a sequential batch poisons the rest (424): retry the failed op and the 424s individually or in a fresh batch.
- Keep MAG&Cie's rule: always inspect each sub-status; the outer 200 means nothing.
