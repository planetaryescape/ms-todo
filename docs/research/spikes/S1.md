# S1: does tasks/delta report checklist item, linked resource and attachment changes?

Run: 2026-09-24 14:11–14:27 UTC, BK's personal MSA, Graph v1.0, throwaway list `ms-todo-spike-2026-09-24`
(its Graph ID is written as `{L}` throughout; the real ID is redacted).
Task under test: "S1 parent task". All requests: `Authorization: Bearer <redacted>`; writes add `Content-Type: application/json`.
Two delta cursors were kept in parallel: plain `tasks/delta` and `tasks/delta?$expand=checklistItems,extensions`.

## Answer

**Yes, fully. Sync strategy (a) applies to checklist items, linked resources and attachment presence.** Every child write
(create, update, delete of checklistItem; create, delete of linkedResource; create, delete of attachment) bumps the parent
task's `lastModifiedDateTime` **and** `@odata.etag`, and the parent appears in the next `tasks/delta` round.
More than that: **`checklistItems` and `linkedResources` are embedded inline in every task representation** (plain GET, collection
GET and delta) with no `$expand` needed. Confidence: high (observed on every step, both cursors).

## `$expand` support

| Request | Status | Effect |
|---|---|---|
| `GET …/tasks/delta?$expand=checklistItems` | 200 | accepted; no visible difference (items are inline anyway) |
| `GET …/tasks/delta?$expand=extensions` | 200 | accepted, **extensions silently not returned** (see S2) |
| `GET …/tasks/delta?$expand=checklistItems,extensions` | 200 | same |
| `GET …/tasks/delta?$expand=linkedResources` / `attachments` | 200 | accepted, no effect |
| `GET …/tasks?$expand=checklistItems` | 200 | full checklist item objects (same as without expand) |
| `GET …/tasks/{T}?$expand=attachments` | 200 | **`attachments` not returned** even though `hasAttachments:true` |
| `GET …/tasks/{T}/attachments` | 200 | returns the attachment metadata (the only way to list them) |

Shape of a task with children, from plain `GET /tasks/{T}` (no $expand):
keys `@odata.etag, body, categories, checklistItems, checklistItems@odata.context, createdDateTime, hasAttachments, id,
importance, isReminderOn, lastModifiedDateTime, linkedResources, linkedResources@odata.context, status, title`.

Inline size: a task with 42 checklist items returned all 42 inline on GET, collection GET and delta (no truncation, no nextLink).

## Gotchas found

1. **`PATCH checklistItem` with only `displayName` resets `isChecked` to false** and clears `checkedDateTime`. Reproduced twice:
   `PATCH {"isChecked":true}` → `isChecked:true, checkedDateTime:14:12:57Z`; then `PATCH {"displayName":"step one renamed again"}`
   → `isChecked:false, checkedDateTime:null` (confirmed by a separate GET). `PATCH {"isChecked":true}` alone keeps the name.
   Invariant: always send `isChecked` with every checklist-item PATCH.
2. Empty child collections are **absent** from the task JSON (no `checklistItems: []`). Absence must be read as "empty", not "unknown".
3. Delta returns the **full task** on every change (all properties, not a diff).
4. Attachments are never inline: only `hasAttachments` flips. Attachment list/metadata needs `GET …/attachments`.
5. Checklist items carry no etag of their own (keys: `createdDateTime, displayName, id, isChecked`, plus `checkedDateTime` when set).

## Conclusion

Strategy (a) holds for checklist items and linked resources, with no `$expand` needed: delta alone keeps them in sync.
Attachments: delta tells you *that* the set changed (parent bump + `hasAttachments`); fetch `/attachments` for tasks whose
`hasAttachments` is true when delta reports them (cheap, and only for those tasks). Extensions: see S2 (bump yes, content no).
Confidence: high.
