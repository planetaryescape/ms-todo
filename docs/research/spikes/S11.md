# S11: does dueDateTime keep a time? startDateTime? reminderDateTime?

Run: 2026-09-24 14:19:42–14:20:10 UTC. Throwaway list `{L}`. Auth header redacted. Mailbox time zone (`GET /me/mailboxSettings/timeZone`): `GMT Standard Time`.

## Answer

- **`dueDateTime`: the time is thrown away.** Graph keeps only the *date*, stored as **midnight in the time zone you sent**, and returns it
  converted to UTC. 17:30 Europe/London on 26 Sep → `2026-09-25T23:00:00.0000000` UTC (midnight BST). 17:30 UTC → `2026-09-26T00:00:00` UTC.
- **`startDateTime`: same truncation**, and **setting `startDateTime` alone also sets `dueDateTime` to the same value.**
  With both given, both are kept (each truncated).
- **`reminderDateTime`: time kept exactly** (converted to UTC): 17:30 Europe/London → `2026-09-26T16:30:00` UTC; 17:30 UTC → 17:30 UTC.
- Windows zone names are accepted too (`"GMT Standard Time"` behaved like Europe/London).
- **`Prefer: outlook.timezone="Europe/London"`** works on GET, collection GET and delta: values come back in that zone
  (`2026-09-26T00:00:00.0000000`, `"timeZone":"Europe/London"`). No `Preference-Applied` header is returned for it.
Confidence: high.

## What BK's existing data looks like (aggregate shapes only, no content)

Across all non-throwaway lists (read-only): due time-of-day in UTC = `23:00` ×41, `00:00` ×41, `20:00` ×4; `completedDateTime` =
`00:00` ×418, `23:00` ×2; 67 recurring tasks, all with `recurrenceTimeZone: "UTC"`; 89 tasks with a reminder.
So real due dates are "midnight somewhere": BST (23:00Z), GMT/UTC (00:00Z) and some other zone (20:00Z = midnight UTC+4).

## Conclusion / mapping rule

- A due date is a **date**, not an instant. Write it as `{"dateTime":"YYYY-MM-DDT00:00:00","timeZone":"<user IANA tz>"}`.
- Read it as a date by converting the returned UTC instant to the user's zone and **rounding to the nearest midnight** (not truncating):
  that gives the right date for all three shapes seen in BK's data (23:00Z, 00:00Z, 20:00Z) and for NY-written dates. Keep the raw
  `dateTime`+`timeZone` in `raw_json`.
- "Date with a time" (`tomorrow 5pm`) **must** map to due date + `reminderDateTime` at that time (+ `isReminderOn:true`). There is no way to store a due *time*. 06's `nlp.time_sets_reminder` stops being optional: a time can only live in the reminder.
- `start <date>` alone silently sets the due date too; the parser/CLI should warn, or always send an explicit due when setting start.
