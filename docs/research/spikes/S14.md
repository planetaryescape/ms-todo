# S14: can a task be copied to another list without losing anything?

Run: 2026-09-25 02:51–03:05 UTC, BK's personal MSA, Graph v1.0, the throwaway list `ms-todo-spike-2026-09-24` (`{L}`) and a list made for the run and deleted after it, `ms-todo-spike-move-target` (`{T}`). IDs are redacted; auth headers were sent and aren't shown. The spike list held 31 tasks before and after.

Asked for rung 5e (D-051): a move is a copy, so what does a copy keep, and which requests make it?

## Answer

**A copy keeps everything but `createdDateTime`, and one POST makes nearly all of it.** A task POST takes its checklist items and its linked resource inline, and they come back exactly: names, order, `isChecked`, and even `checkedDateTime` and the items' own `createdDateTime`. With our extension inline too (S13), one attributable request creates the copy with every field and child except attachments. Attachments are copied one by one, and their bytes survive exactly. Confidence: high.

Three surprises changed the design (D-051):

1. **A task holds at most one linked resource.** A second POST to `…/linkedResources` is 400 `invalidRequest` "Linked Resource already exists." (inner code `LinkedResourceSizeExceeded`), whatever its `applicationName`; two inline on a create are 400 "Only one item in linkedResources is allowed." The brief's "2 linked resources" can't exist.
2. **An upload session's bytes go to `<uploadUrl>/content`, with the bearer token.** The `uploadUrl` Graph returns is `https://graph.microsoft.com/v1.0/users/<address>/todo/lists/{T}/tasks/{t}/attachmentSessions/{s}`. A PUT to it without a token is 401 "Access token is empty."; with one it's 404 `UnknownError` (the `/me/…` form too). Appending `/content` works: 200 with `nextExpectedRanges` for each chunk but the last, 201 with a `Location` header and no body for the last. Found in Microsoft's "Attach files to a To Do task" guide after the 404.
3. **A recurring task's dates must be written in its recurrence's zone, and a GET reports that zone as UTC.** A task created with due 28 Sep London and `recurrenceTimeZone: Europe/London` reads back from a GET as due `2026-09-27T23:00Z` with `recurrenceTimeZone: "UTC"` (the POST's own answer still says London). Copying that recurrence with the due date written as 28 Sep London made Graph move the copy's due date *and* the series' `startDate` to the 29th. Written as midnight of the local day in the zone the recurrence reports (28 Sep 00:00 UTC), the copy kept the day, the pattern and the range exactly, for a daily London series, a daily UTC one (as the To Do apps write them) and a weekly series started a week earlier. A one-off task's dates go back as their local day in the user's zone, as undo already writes them (D-048).

## What survived (source vs copy, field by field)

The copy was made as the design makes it: `POST /me/todo/lists/{T}/tasks` with the fields, `checklistItems`, `linkedResources` and our extension inline, then each attachment.

| Field | Kept? | Notes |
|---|---|---|
| `title`, `body` (text), `importance`, `status`, `categories`, `isReminderOn` | yes | |
| `reminderDateTime` | yes | the same instant |
| `dueDateTime`, `startDateTime` | yes, as days | with rule 3; the zone Graph stores may differ (London in, UTC out), the day doesn't |
| `recurrence` | yes | pattern and range equal, with rule 3 |
| `completedDateTime` | yes | settable on create: a probe POST with `status: completed` and `completedDateTime` 20 Sep kept 20 Sep; without one, Graph stamps today (midnight UTC) |
| `createdDateTime` | **no** | stamped at the copy's creation; sent on a create, it's ignored (201, no error). Kept as `originalCreatedAt` in our extension |
| `lastModifiedDateTime`, `id`, `@odata.etag` | no | Graph's own |
| checklist items | yes | order, `displayName`, `isChecked`, `checkedDateTime`; `createdDateTime` too, to the second (`…23.3795339Z` came back `…23Z`); new item IDs |
| linked resource | yes | `webUrl`, `applicationName`, `displayName`, `externalId`; new ID |
| our extension | yes | every field sent; `opId` is the move's own (S13) |
| `hasAttachments` | yes | true once the attachments are added |
| attachments | yes | name, `contentType`, `size` metadata equal; bytes equal by sha256 |

Attachments, both directions checked by downloading `…/attachments/{a}/$value`:

| File | Bytes | Metadata `size` | sha256 equal |
|---|---|---|---|
| a text file, direct POST with `contentBytes` | 63 | 321 | yes |
| random bytes, upload session in two chunks | 4,317,761 | 4,317,988 | yes |

The metadata `size` isn't the byte count (it counts some overhead), so checks compare downloaded bytes, not `size`. A single `GET …/attachments/{a}` returns `contentBytes` even for the 4 MB file, but `$value` is the plain way to get bytes.

After the copy, `DELETE /me/todo/lists/{L}/tasks/{source}` was 204 and a GET of it 404; `GET /me/todo/lists/{T}` was 200.

## Conclusion

- Create the copy in **one POST** carrying fields, checklist items, the linked resource and our extension (`opId`, `originalCreatedAt`). An unknown outcome of that POST is attributable by `opId` (S13), children included. The per-child batches the brief allowed for (S10) aren't needed.
- Copy attachments one at a time: under 3 MiB a POST, else an upload session to `<uploadUrl>/content` with the token. A lost answer to either is unattributable, so it pauses the move (04).
- Write a recurring task's due and start dates as midnight of their local day in the zone its recurrence reports; a one-off's as its local day in the user's zone.
- Check the copy by downloading its attachments and comparing sha256, not `size`.
- Keep `createdDateTime` as `originalCreatedAt`.
