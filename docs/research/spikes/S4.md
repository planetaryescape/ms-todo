# S4: deltaLink lifetime and expiry behaviour

Run: 2026-09-24 14:11–14:31 UTC (plus a background prober, see below). Auth redacted. The real deltaLinks saved for a later
replay are kept outside the repo, on the machine that ran the spikes (mode 600). None appears here; any shown are `…$deltatoken=<redacted>`.

To test deleted-list behaviour, three extra short-lived lists were created and deleted within seconds, all named with the spike prefix:
`ms-todo-spike-2026-09-24-s4-deleteme` (14:16:33–14:16:34), `…-s4b-deleteme` (14:17:04–14:17:05), `…-s4c-deleteme` (14:25:45, same second).
No other list was touched.

## Answer

| Case | Status | Body |
|---|---|---|
| A made-up delta token (`garbage123`) on tasks or lists delta | **400** | `{"error":{"code":"BadRequest","message":"Badly formed token.",…}}` (no innerError code) |
| Real token, truncated, or one character flipped at the end or in the middle | **400** | "Badly formed token." |
| Real token from another scope (lists token on tasks/delta, or tasks token on lists/delta) | **410** | `{"error":{"code":"SyncStateNotFound","message":"The delta token is no longer valid, and the app must reset the sync state.","innerError":{"code":"SyncStateInvalid",…}}}` |
| A real lists deltaLink issued 14:11:24, used once at 14:14, replayed at 14:17:40 and every time after | **410** | `{"code":"SyncStateNotFound", same message, "innerError":{"code":"SyncStateNotFound"}}` (request-id 054b1145-28d8-49d2-bac3-9446186f5b45) |
| tasks deltaLink of a **deleted list** | **200, empty** `value:[]` and a fresh deltaLink | no error at all |
| `$skiptoken=garbage` | 400 | |

**Token structure:** `$deltatoken` = two base64url segments joined by `.`: an opaque blob (80 bytes for plain delta, 256 bytes with
`$expand`; a constant 16-byte prefix, likely key id / IV) plus a 32-byte tag (looks like an HMAC-SHA256). Any bit change → "Badly formed
token". No readable timestamp; lifetime can't be read from the token.

**Reuse:** a deltaLink can be replayed many times; issuing and using newer links does not invalidate older ones (A, B, C chain test:
all returned 200 and the same changes).

**Lifetime:** unknown beyond the observation window (see prober table). One lists deltaLink died with `SyncStateNotFound` after ~6 min
for no reason we could identify; five other links (lists and tasks, including ones spanning list deletions) stayed valid for 12–18+ min.
Hypotheses tested and refuted: age alone (a 5-min-older tasks token survived), reuse, list creation, deleting a list the token never saw.

**Deleted lists:**
- `lists/delta` reports a deleted list as `{"@removed":{"reason":"deleted"},"id":…,"isOwner":…,"isShared":…,"wellknownListName":…}`
  if the cursor had seen it; a list created and deleted between two rounds doesn't appear at all.
- After `DELETE /me/todo/lists/{id}` (204), `GET /lists/{id}` is 404 and it's gone from `/lists`, **but `GET /lists/{id}/tasks`, `tasks/delta`
  and even `POST /lists/{id}/tasks` (201!) keep working** for a while (observed 20+ s after delete). A write to a deleted list silently succeeds into a ghost.
  The two ghost tasks were deleted again (204) afterwards.
- A deleted list's tasks deltaLink returns 200 with nothing: it never reports the deletion.

## Conclusion

- Treat **both** 410 `SyncStateNotFound` (any innerError) **and** 400 "Badly formed token." as "reset this cursor", then run the
  reconciliation in 04. Expect 410s in normal operation, not only after days: a lists resync is 1–2 requests, a tasks resync is ~1 request per 50 tasks.
- Deleted lists are detected **only** by `lists/delta` `@removed` (or 404 on `GET /lists/{id}`). The per-list tasks cursor will not tell you.
  The outbox must check that a target list still exists (not tombstoned) before sending, and on `@removed` for a list, fail any pending ops for it
  rather than letting them "succeed" into the ghost.
- **A 404 or 5xx on a delta replay isn't proof of anything**: the same valid links returned 404/500 once, then 200 a minute later.
  Retry with backoff and keep the cursor. Only 410 or "Badly formed token" resets it, and only a lists `@removed` or `GET /lists/{id}` 404 tombstones a list.
- The saved links (kept outside the repo) should be replayed in a few days to measure real lifetime.
Confidence: high on error shapes; low on lifetime.
