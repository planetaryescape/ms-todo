# S17: how does Graph set `isReminderOn`?

Run: 2026-09-26, on the `livetest` instance's sign-in, Graph v1.0, probe tasks in the throwaway list `ms-todo-spike-005-2308` (and a move into `ms-todo-spike-005b-2308`). IDs are redacted; auth headers were sent and aren't shown. Each probe used a reminder time `T` a few days ahead.

Asked for [issue 005](../../issues/005-reminder-off-after-reopen.md): completing a task turned its reminder off, reopening left it off, and moving such a task failed its check. Can a write set `isReminderOn` either way while keeping the time?

## Answer

**No. Graph derives `isReminderOn` and ignores a written one.** Writing `reminderDateTime` turns the reminder on; a transition to `completed` turns it off and keeps the time; writing `reminderDateTime: null` turns it off and removes the time.

| Request | On | Result |
|---|---|---|
| POST `{isReminderOn: false, reminderDateTime: T}` | new task | on, time kept |
| PATCH `{isReminderOn: false}` | open task with a time | still on |
| PATCH `{isReminderOn: false, reminderDateTime: T}` | open task with a time | on |
| PATCH `{reminderDateTime: null}` | open task with a time | off, time gone |
| PATCH `{status: completed}` (a transition) | open task with a time | off, time kept |
| PATCH `{status: completed, isReminderOn: false}` | open task with a time | off, time kept |
| PATCH `{status: completed, reminderDateTime: T}` | open task with a time | completed, **on** |
| PATCH `{status: completed, isReminderOn: false, reminderDateTime: T}` | open task with a time | completed, **on** |
| PATCH `{isReminderOn: true}` | completed task, reminder off | still off |
| PATCH `{status: notStarted, isReminderOn: true}` | completed task, reminder off | notStarted, **still off** |
| PATCH `{isReminderOn: true}` | the same task after that reopen | still off |
| PATCH `{reminderDateTime: T}` (its own time) | reopened task, reminder off | on |
| PATCH `{status: notStarted, reminderDateTime: T}` | completed task, reminder off | notStarted, on |
| PATCH `{status: notStarted, isReminderOn: true, reminderDateTime: T}` | completed task, reminder off | notStarted, on |
| POST `{status: completed, completedDateTime: C, reminderDateTime: T}` | new task | completed, on, `completedDateTime` kept |
| PATCH `{status: completed}` | that completed task (no transition) | still on |

So a time written with a completion wins over the completion, and no request found turns a reminder off with its time kept on an open task (short of completing it, which on a repeating task rolls it forward).

Confidence: high for what was seen.

## What it changes

- Reopening, and undoing a completion, turn the reminder back on by writing the task's own `reminderDateTime` again with the status (D-060). `isReminderOn: true` goes with it only so the cache shows it at once.
- Undoing a reopen writes the time back only if the reminder was on before it, or the completion would come back with its reminder on.
- A move's copy of a task whose reminder is off comes back on, and that is accepted: the check expects it on then, and compares the copy's actual flag (D-060).
- The Graph double (`crates/fake-graph`) models these rules.
